# 第 18 章 ソフトウェア工学の基礎

> **この章の学習目標**：「コードを書く」から「ソフトウェアを造る」へ——要件、構造、テスト、デバッグ、バージョン、規範の六点セットを、すべて zhc のツールチェーンで落地させる。
> **この章を読み終えると答えられる問い**：ユニットテストはなぜ重要なのか？デバッグの第一原則は何か？セマンティックバージョニングはどう読む？

---

## 18.1 定義：ソフトウェア工学とは何か

**定義**：コードを書くのは「思い付きをプログラムにする」こと。ソフトウェア工学は「**プログラムを保守可能に、検証可能に、協働可能にする**」ための一揃いの規律：

| 個人のコード | エンジニアリングのプロジェクト |
|---|---|
| 動けばよい | 他人が読めて、直せる |
| 自分は何を変えたか覚えている | git がすべての変更を記録する |
| 一回走らせて結果を見る | 自動テストがすべての機能を守る |
| 環境は自分のマシンにある | 文書化 + 再現可能なビルド |

**なぜか**：本物のソフトウェアは時間の 9 割を**修正**に使う——ゼロから書くのではない。コードを読む時間は書く時間の 5-10 倍。エンジニアリングの規律が仕える相手は「未来の読者」（半年後の自分自身を含む）。

## 18.2 要件分析：先に「何を作るか」を考える

**思想**：コードを書く前に三つの問いに答える——**誰が使う**（ユーザー）、**何を解決する**（問題）、**どうなれば成功か**（受け入れ基準）：

1. **一文の要件**：一文で機能を言い切る（「摂氏を華氏に変換して表示するコマンドラインツール」）；
2. **受け入れ基準**：「どうなれば完成か」を書く（入力 25℃ で出力 77℉。負の数もサポート）；
3. **最小で使えるもの**：まず最も中核の一つの道筋を作り、それから反復する（まず温度変換、次に一括、その次に対話）。

**実践**：「入力が不正かも」を `オプション` で扱うのは要件分析の直接の産物——要件が「入力は任意のテキストかもしれない」と言えば、設計は**`オプション` を返す解析関数**を書く。**要件がエラー処理の戦略を決める**。

## 18.3 プロジェクト構造と再現可能なビルド

**定義**：プロジェクト = 設定の宣言（`cjpm.toml`）+ 約束のディレクトリ（`src/`）+ 文書化された環境（第 1 章）：

```toml
[package]
name = "わたしのプログラム"
version = "0.1.0"
edition = "1.0.5"

[dependencies]
libdemo = { path = "../libdemo" }
```

**三つの規律**：

- **依存の宣言化**：すべての外部依存を `[dependencies]` に書く——他人がプロジェクトを clone したら `cjpm fetch` の 1 コマンドで揃う；
- **環境の文書化**：SDK バージョン、環境変数（`CANGJIE_HOME`/`LD_LIBRARY_PATH`）、ビルドコマンドを README に書く——別のマシンでも再現できる（第 1 章）；
- **自動化スクリプト**：繰り返しの動作はスクリプト化——このプロジェクトの `scripts/release.sh`（オフラインパッケージ作成）と `acceptance.sh`（52 項目の受け入れ）がまさに「プロセスをコマンドにする」手本。

**ツールチェーンコマンド早見**：

```bash
zhc init わたしのぷろじぇくと   # プロジェクトを作成（src/main.zc が生成される。テンプレは zh 方言なので src/main.jc にリネームして使う）
zhc run src/main.jc      # 転訳して実行
zhc check src/main.jc    # 検査だけで実行しない（CI でよく使う）
zhc lint --fix src/main.jc   # スタイル検査 + 自動修正
zhc test                 # すべての方言テストを実行
zhc eject src/main.jc    # 公式 .cj ソースを書き出す
```

**ソースの中のパッケージ宣言**：`cjpm.toml` の `[package]` は**プロジェクト設定**。個々の `.jc` ソースの**先頭行**には `パッケージ 名前.空間` と書いて自分の**ソースパッケージ**を宣言することもできる——プロジェクトのファイルが増えたら、パッケージでコードを層に分ける（例：`パッケージ 図書.管理`、`パッケージ 図書.画面`）。名前の重複を避けられるうえ、`うち` で可視性を制御できる（付録 A）：

```jc
パッケージ 図書.管理

メイン() {
    ひょうじ("パッケージ宣言付きのファイルも、zhc run でそのまま実行できる")
}
```

単一ファイルの小さな練習ではパッケージ宣言は省略してよい。複数ファイルのプロジェクトは「先頭行にパッケージを書き、ファイル名はパッケージ内の主たる型の名前にする」約束を守ろう。

**ビルドのパイプライン**（この鎖を理解すれば zhc のすべてを理解したことになる）：

```
方言ソース .jc → zhc 転訳（言語パックの語表を引く）→ 公式ソース .cj → cjc コンパイル → バイナリ
```

## 18.4 ユニットテスト：コードに保険を掛ける

**定義**：小さなコードを書いて、別のコードの振る舞いを検証する——テストのないプログラムはブレーキのない車のようなもの。倉頡の標準ライブラリはテストフレームワークを内蔵し、zhc が全日本語で包んでいる：

```jc
いれる 標準テストマクロ.*
いれる 標準テスト.*

関数 評価(てん: せいすう): 文字列 {
    もし (てん >= 60) { かえす "合格" }
    かえす "不合格"
}

@テスト
関数 テスト評価() {
    @期待(評価(85), "合格")        // 式の結果が 85 点の評価になることを期待
    @期待(評価(40), "不合格")      // 境界と普通をそれぞれ 1 つずつ
}
```

プロジェクトルートで実行：

```bash
zhc test
```

```
[ 通過 ] テスト：テスト評価
集計：合計 1
    通過： 1, スキップ： 0, エラー： 0
    失敗： 0
```

（実行時の文言は zhc 側の表示形式による。上は zh 教程と同じ書式の例）

**テスト三原則**：

| 原則 | 意味 | 反例 |
|---|---|---|
| **決定性** | 同じ入力はいつも同じ結果 | テストが現在時刻/乱数に依存している |
| **独立性** | 各テストは互いに依存せず、単独で走れる | テスト B がテスト A の先行実行に依存している |
| **可読性** | 失敗の情報が「どの仮定が破られたか」を語る | `たしかめる(結果 == 5)` が文脈を示さない |

**なぜ書く価値があるか**：

- **回帰の保護**：コードを変えたら一回走らせて、何かを壊していないかすぐ分かる——リファクタリングの底力；
- **テストはドキュメント**：テストは「この関数はどう使うべきか、結果はどうなるか」を示す——コメントより信頼できる（コメントは古びる。テストが古びれば赤くなる）；
- **テスト駆動設計**：テストを書くとき「入出力の契約」を考えざるを得ない——ついでに関数の設計がきれいになる。

**アサーションの選択**：`@期待(式, 値)`（マクロ。診断に式のテキスト付き）> `断言相等(実際, 期待)`（関数）> `たしかめる(条件, "情報")`（真偽）。

## 18.5 デバッグの方法論：エラーは敵ではなく手掛かり

**思想**：デバッグ = 「間違い得る範囲」を狭めて特定するまで。zhc は三つの武器を与える：**教学診断**（第 14 章のエラー処理 + 四段式：レベル/位置/💡ヒント/修正例）、**lint 静的解析**、**expand 転訳ビュー**。

**五段階デバッグ法**：

1. **まず分類**：コンパイルエラー（診断コードの接頭辞 lex/parse/name/sema/pkg がどの段階か教えてくれる）か、実行エラー（例外/ロジックミス）か？
2. **最小限に再現**：エラーを出すコードを最小まで縮める——最小の再現がしばしば真犯人を暴く（無関係な部分を削る）；
3. **エラーの全文を読む**：zhc の診断はファイル:行:列 + 💡 + 修正例を伴う——**先にヒント通り直してから、なぜそうなのかを理解する**；
4. **二分で位置を絞る**：データフローの途中に `ひょうじ` を挟んでどこからおかしくなるかを見る（プリントデバッグ）。あるいはコードの半分をコメントアウトして、エラーが消えるのがどちらの半分かを見る；
5. **修正を検証**：直したらテストを走らせ、わざと一度同じ過ちを犯して理解を確認する。

**よくある病根**（第 16 章の思想と照らして自己点検）：

| 症状 | 病根 | 自己点検 |
|---|---|---|
| 値が「こっそり」変わった | 可変性の暴走 | `おく`/`構造体`（コピー意味論）を使うべきでは？ |
| 空値でクラッシュ | アンラップが早すぎ | `マッチ`/`なければきてい` を使うべきで、`なければれいがい` では？ |
| 並行の結果が不定 | 共有の可変状態 | `同期` を足すか、不変の設計に変える（第 14 章）？ |
| 振る舞いが順序に依存 | ハッシュ容器の走査 | マップ/集合の順序に依存してはいけない（第 11 章）？ |

## 18.6 バージョン管理とリリース

**定義**：**バージョン管理（git）**：エンジニアリング協働の礎石——すべての変更を記録し、ロールバックと協働を支える：

```bash
git init                # リポジトリを初期化
git add ファイル            # ステージング
git commit -m "メッセージ"    # コミット（メッセージには「何を変えたか、なぜか」を書く）
git log                 # 履歴を見る
```

**コミットメッセージの規範**：一行のタイトル（動詞で始める：`追加`/`修正`/`リファクタリング`/`ドキュメント`）+ 必要なら本文で「なぜ」を説明。

**セマンティックバージョニング**（SemVer）：`メジャー.マイナー.パッチ`——バージョン番号を読めば互換性が分かる：

| バージョン | 意味 |
|---|---|
| `0.1.0` | 0.x：未安定、何を変えてもよい |
| `1.0.0` | 最初の安定版 |
| `1.2.0` | マイナー+1：機能を追加（後方互換） |
| `1.2.3` | パッチ+1：bug を修正（完全互換） |
| `2.0.0` | メジャー+1：**破壊的変更**（`1.x` を使ったコードは直す必要がある） |

**リリースの流れ**（このプロジェクトの例）：全量実測（チュートリアルのコードブロックを全部実行）→ 52 項目の受け入れスクリプト → リリースパッケージ作成（`scripts/release.sh`：コンパイル + 言語パック + 起動スクリプト）→ 更新の説明を書く → tag を打つ。**リリース前に必ずテスト。リリース後には必ず記録**。

## 18.7 コード規範と読みやすさ

**定義**：コードは機械に実行させるために書くが、人に読ませるためにも書く。スタイルが統一されていれば、チームの協働は喧嘩にならない：

```bash
zhc lint src/main.jc          # スタイル検査（全角句読点/末尾の空白/行の長さ…）
zhc lint --fix src/main.jc    # 自動修正
```

**読みやすさの五則**（方言版）：

1. **命名は意図を語る**：`変数 総点` は `変数 s` よりまし——日本語の命名は意図をより直接にする；
2. **関数は小さく専門に**：一つの関数は一つのことだけ（20 行を超えたら分割を考える）；
3. **コメントは「なぜ」を語る**：コードは「どうやるか」、コメントは「なぜそうするか」；
4. **DRY**：Don't Repeat Yourself——重複コードは関数/ジェネリクス/マクロへ抽出する。だが**二回の重複で抽象化を急ぐな**（三回以上になってから言う）；
5. **宣言的を優先**：`こす`/`うつす` のパイプラインは手書きループより読みやすい（第 11 章）。

**コードレビュー**：自分のコードを他人に見せる（あるいは他人のを見る）——レビューは揚げ足取りではなく**四人の目**の原則：コードを書いた人には盲点がある。第二の目が品質の関門。レビューの重点：ロジックの正しさ、境界のケース、命名、テストのカバレッジ。

## 18.8 要件から納品まで：完全なケース

この章の六点セットを一つの完全な流れに串刺しにする——「温度変換コマンドラインツール」（第 19 章で完全な実戦プロジェクトを作る。ここでは最小の流れをデモする）：

**① 要件**：一文 + 受け入れ基準 + 最小で使えるもの：

```
要件：コマンドラインで摂氏を入力し、華氏を出力する
受け入れ：入力 25 → 出力 77.0；入力 abc → 「数字ではない」と出してクラッシュしない
```

**② 設計**：`オプション` で解析の失敗を扱う（予期した失敗。第 14 章）。`メイン` は入力の読み取り、解析、計算、表示：

```jc
いれる 標準環境.*
いれる 標準変換.*
いれる 正規表現.*

関数 華氏変換(摂氏: じっすう): じっすう {
    かえす 摂氏 * 9.0 / 5.0 + 32.0
}

関数 摂氏よみ(ぶん: 文字列): オプション<じっすう> {
    もし (せいき("^\\d+(\\.\\d+)?$").ヒット(ぶん)) {   // アンカー：文字列全体が数字のときだけ通す（錨がないと取りこぼす）
        かえす あり(じっすう.かいせき(ぶん))                    // 数字 → 成功
    }
    かえす なし                                        // それ以外 → 失敗（予期した失敗はオプション）
}

メイン() {
    おく にゅうりょく = よみこむ()
    マッチ (摂氏よみ(にゅうりょく)) {
        場合 あり(摂氏) => ひょうじ("${華氏変換(摂氏)}")
        場合 なし => ひょうじ("数字ではない")
    }
}
```

**③ テスト**：実装より先にテストを書く（または並行して）：

```jc
いれる 標準テストマクロ.*
いれる 標準テスト.*

関数 華氏変換(摂氏: じっすう): じっすう {
    かえす 摂氏 * 9.0 / 5.0 + 32.0
}

@テスト
関数 テスト華氏変換() {
    @期待(華氏変換(25.0), 77.0)
    @期待(華氏変換(-40.0), -40.0)     // 境界：摂氏マイナス四十は華氏マイナス四十と等しい
}
```

**④ テストを走らせて手動検証**：`zhc test` が全部緑。手で `abc` を入力して、優雅に扱われるのを確かめる（実測での表示は `77.000000`。値は 77.0 と同じ）。

**⑤ コミット**：`git add . && git commit -m "追加：温度変換ツール"`。`0.1.0` の tag を打つ。

**⑥ 振り返り**（任意）：測っていない境界はないか（`0` 度、最大値）？関数を分割すべきか？——**小さく進み、一歩ごとに検証できる**。

## 練習

1. 18.8 の温度ツールに機能を一つ足そう（例：「`終了` と入力するまで複数回入力を受け付ける」）。要件 → テスト → 実装 → コミットの全フローを歩こう；
2. `zhc lint` で自分のプロジェクトを検査し、スタイルの問題を全部直してコミットしよう；
3. `評価` 関数に境界テストを足そう：`60`（合格ライン）、`59`、`100`、`0`；
4. すでに書いた関数を一つ選び、「五段階デバッグ法」でわざと bug を作ってから位置を特定して直そう；
5. このプロジェクトの `scripts/acceptance.sh` を読んで、それがどんな「重要な振る舞い」を守っているか言おう——自分が作者なら、どんな受け入れ項目を一つ足す？

## まとめ

- ソフトウェア工学 = プログラムを保守可能・検証可能・協働可能にする規律。要件はコードに先立ち、受け入れ基準は実装に先立つ；
- プロジェクトの三種の神器：設定の宣言（cjpm.toml）+ 約束のディレクトリ（src/）+ 文書化された環境；
- ユニットテスト：`@テスト` + `@期待`、`zhc test` で一括実行。決定性/独立性/可読性の三原則；
- デバッグ五段階：分類 → 最小再現 → 全文を読む → 二分で位置 → 修正を検証；
- git + セマンティックバージョニング + リリースの流れで変更が追跡可能に。`zhc lint` でスタイル規範がゼロコストに。

## 考えてみよう

1. 「テストはドキュメント」——なぜテストはコメントより信頼できる？（ヒント：コメントは古びる。テストが古びれば赤くなる）
2. なぜ「二回の重複で抽象化を急ぐな」なのか？（ヒント：抽象化が早すぎる = 方向を間違えた推測。三回目の重複でパターンがはっきりする）
3. セマンティックバージョニングの `1.2.0` と `1.2.3` の違いは何か？なぜメジャー `2.0.0` は慎重に扱うべきか？
4. 五段階デバッグ法で、なぜ「最小に再現」が「エラーの全文を読む」より先なのか？（ヒント：エラーは連鎖反応かもしれない）
