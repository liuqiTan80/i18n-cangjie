# 第 19 章 総合実戦：完全なプロジェクト

> **この章の学習目標**：全書の知識を一つの**完全な実プロジェクト**に串刺しにする——要件 → 設計 → テスト先行 → 実装 → デバッグ → リファクタリング → コミット → リリース。ソフトウェア工学の全フロー（第 18 章の方法論の実戦落地）を一巡する。
> **この章を読み終えると答えられる問い**：「使える」プログラムは、一文の要件からどう育っていくのか？テスト先行はなぜコードをきれいにするのか？

---

## 19.1 プロジェクトの選定：数当てゲーム

**要件（一文）**：コンピュータが 1 から 100 の整数を心に思い浮かべる。あなたが当てる。コンピュータは「小さい」「大きい」「正解」を教え、あなたが使った回数を数える。

**受け入れ基準**：

- 毎ゲーム、ランダムに 1..100 の数を思い浮かべる（実行のたびに違う）；
- 入力が不正（数字でない）なら促して入力し直し、**クラッシュしない**；
- 当てたら回数を表示し、「もう一局？」と尋ねる；
- 「`終了`」と入力すればいつでも終了。

**設計の決定**（ひとつひとつが本書の知識点に対応）：

| 要件点 | 設計 | 知識点 |
|---|---|---|
| 乱数 | ランダムモジュール | いれる とモジュールパス（第 10 章） |
| 入力が不正かも | `オプション` を返す解析関数 | 予期した失敗はオプション（第 14 章） |
| 当たるまでループ | `あいだ (真)` + `ぬける` | ループ制御（第 6 章） |
| 大小の比較 | `もし/またもし` | 分岐（第 5 章） |
| もう一局 | 外側ループ + 真偽の状態 | ループの入れ子（第 6 章） |

## 19.2 テスト先行：まずテストを書く

**思想**：「この関数はどう振る舞うべきか」のテストを先に書き、それから実装する——テストは要件の実行可能な版。中核のロジックは**純関数**（入出力に依存せず、テストしやすい）へ切り出す：

```jc
いれる 標準テストマクロ.*
いれる 標準テスト.*
いれる 正規表現.*
いれる 標準変換.*

// —— テストされる関数（19.3 で正式実装。ここで先に振る舞いを決める）——

関数 はんだん(ひみつ: せいすう, あて: せいすう): 文字列 {
    もし (あて < ひみつ) { かえす "小さい" }
    またもし (あて > ひみつ) { かえす "大きい" }
    かえす "正解"
}

関数 よみとる(ぶん: 文字列): オプション<せいすう> {
    もし (せいき("^\\d+$").ヒット(ぶん)) {   // アンカー ^...$：文字列全体が数字のときだけ通す（\d+ は包含マッチ）
        かえす あり(せいすう.かいせき(ぶん))
    }
    かえす なし
}

@テスト
関数 テストはんだん() {
    @期待(はんだん(50, 30), "小さい")     // 小さすぎ
    @期待(はんだん(50, 70), "大きい")     // 大きすぎ
    @期待(はんだん(50, 50), "正解")     // 正解
    @期待(はんだん(1, 1), "正解")       // 境界：最小値
    @期待(はんだん(100, 100), "正解")   // 境界：最大値
}

@テスト
関数 テストよみとる() {
    @期待(よみとる("42").なければれいがい(), 42)   // 合法な入力
    @期待(よみとる("abc").なければきてい({ => 0 }), 0)   // 不正な入力 → 受け皿の 0
    @期待(よみとる("").なければきてい({ => 0 }), 0)      // 空入力 → 受け皿の 0
    @期待(よみとる("a1").なければきてい({ => 0 }), 0)    // 境界：数字を含むが全部数字ではない（錨がないと取りこぼす！）
    @期待(よみとる("1a").なければきてい({ => 0 }), 0)    // 境界：後ろに文字
}
```

**注意**：テスト先行では関数を**先に宣言だけ書く**（偽の実装でもよい）。テストを走らせて失敗（赤）を見てから、実装して通す（緑）——これを「赤-緑-リファクタリング」のリズムと呼ぶ。上のコードは完全な実装をそのまま載せたが、実際の作業では先に関数の中身を消して失敗を一回走らせる。

## 19.3 実装：完全なゲーム

**プロジェクト構造**（`zhc init` で作成）：

```
数当て/
├── cjpm.toml
└── src/
    └── main.zc
```

**完全なコード**（`src/main.zc`。zhc init のテンプレは zh 方言なので、中身を日本語の識別子で書き直す）：

```jc
いれる 標準環境.*
いれる 標準変換.*
いれる 正規表現.*
いれる ランダム.*
いれる 標準テストマクロ.*
いれる 標準テスト.*

// —— 中核ロジック：純関数（テスト可能）——

関数 はんだん(ひみつ: せいすう, あて: せいすう): 文字列 {
    もし (あて < ひみつ) { かえす "小さい" }
    またもし (あて > ひみつ) { かえす "大きい" }
    かえす "正解"
}

関数 よみとる(ぶん: 文字列): オプション<せいすう> {
    もし (せいき("^\\d+$").ヒット(ぶん)) {   // アンカー：文字列全体がすべて数字でなければならない
        かえす あり(せいすう.かいせき(ぶん))
    }
    かえす なし
}

// —— 対話ロジック：一局のゲーム ——

関数 いっきょく() {
    おく 生成器 = Random()                    // 乱数生成器（公式クラス名。方言では未収録なのでこのまま）
    おく ひみつ = 生成器.つぎせいすう(100) + 1   // 1..100（nextInt64(100) は 0..99）
    変数 かいすう = 0
    ひょうじ("私は 1 から 100 の整数を思い浮かべた。さあ、当てて！")
    あいだ (真) {
        かいすう += 1
        ひょうじ("${かいすう}回目の予想：")
        おく にゅうりょく = よみこむ()
        もし (にゅうりょく == "終了") { かえす }          // いつでも終了
        おく かず = よみとる(にゅうりょく).なければきてい({ => -1 })   // 無効な入力は受け皿の -1
        もし (かず == -1) {
            ひょうじ("数字を入力してね（または「終了」と入力）")
            かいすう -= 1                       // 無効な入力は回数に数えない
        } でなければ {
            おく けっか = はんだん(ひみつ, かず)
            もし (けっか == "正解") {
                ひょうじ("🎉 正解！答えは ${ひみつ}、使ったのは ${かいすう} 回。")
                かえす
            } でなければ {
                ひょうじ("${けっか}、もう一度！")
            }
        }
    }
}

// —— 入口 ——

メイン() {
    ひょうじ("== 数当てゲーム ==")
    あいだ (真) {
        いっきょく()
        ひょうじ("もう一局？（終了 と入力すれば終了。それ以外のキーで続行）")
        もし (よみこむ() == "終了") { ぬける }
    }
    ひょうじ("さようなら！")
}
```

> 💡 なぜここで `マッチ` を使わないのか？公式 1.0.5 の実測：`マッチ` の分岐本体は**式**でなければならない（`場合 X => 式`）。複文の分岐をブロックで書くと「`=>` を期待」とエラーになる。だから複文の分岐は `なければきてい` の受け皿 + `もし/でなければ` にした——効果は同じで、しかもより率直（第 13 章の `マッチ` 式本体の書き方は 19.7 の挑戦 5 で練習できる）。

**実行**：

```bash
zhc run src/main.jc
```

**実測の一局**（秘密が 62 だった例）：

```
== 数当てゲーム ==
私は 1 から 100 の整数を思い浮かべた。さあ、当てて！
1回目の予想：
50
小さい、もう一度！
2回目の予想：
75
大きい、もう一度！
3回目の予想：
62
🎉 正解！答えは 62、使ったのは 3 回。
もう一局？（終了 と入力すれば終了。それ以外のキーで続行）
終了
さようなら！
```

**ブロックごとの分解**（このプロジェクトで使うすべて）：

| コード | 役割 | 知識点 |
|---|---|---|
| `生成器.つぎせいすう(100) + 1` | 1..100 の乱数を生成 | モジュール導入（第 10 章）。`Random`/`nextInt64` は公式ライブラリ名（zh 語表でも未収録。そのまま使える） |
| `よみとる` が `オプション` を返す | 不正な入力でもクラッシュしない | 予期した失敗はオプション（第 14 章） |
| `よみとる(にゅうりょく).なければきてい({ => -1 })` | 無効な入力は -1 で受け流し、クラッシュしない | オプションの受け皿（第 14 章） |
| `あいだ (真)` + `ぬける`/`かえす` | 条件が満たされるまで無限ループ | ループ制御（第 6 章） |
| `かいすう -= 1` | 無効な入力は回数に数えない | 複合代入（第 9 章） |
| `はんだん` 純関数 | 中核ロジックを独立させてテスト可能に | 関数設計（第 7/8 章） |

## 19.4 テストとデバッグ

**テストを走らせる**：

```bash
zhc test
```

```
[ 通過 ] テスト：テストはんだん
[ 通過 ] テスト：テストよみとる
集計：合計 2
    通過： 2, スキップ： 0, エラー： 0
    失敗： 0
```

（実行時の文言は zhc 側の表示形式による。上は zh 教程と同じ書式の例）

**わざと bug を作ってデバッグを練習**：`はんだん` の中の `あて < ひみつ` を `あて <= ひみつ` に変える——テストを走らせると、`@期待(はんだん(50, 50), "正解")` が**赤**になる（「小さい」になる）。これが回帰テストの価値：壊したものがすぐ現れる。

**デバッグの流れ**（五段階法。第 18 章）：

1. 分類：これはロジックエラー（コンパイルは通り、振る舞いがおかしい）；
2. 最小再現：`はんだん(50, 50)` の 1 行で足りる；
3. 出力を読む：`@期待` の失敗は実際の値（"小さい"）と期待値（"正解"）を表示する；
4. 二分で位置：`<=` か `<` かの問題——境界を比較する；
5. 修正を検証：`<` に戻して `zhc test` が全部緑。

## 19.5 リファクタリング：コードをよりきれいに

**定義**：リファクタリング = 振る舞いを変えず、構造だけを変える（テストが壊していないことを保証する）。このプロジェクトでできるリファクタリング：

**① 定数の抽出**（魔法の数字 1、100 は悪い匂い）：

```jc
いれる ランダム.*
定数 最小 = 1
定数 最大 = 100

関数 いっきょく() {
    おく 生成器 = Random()
    おく ひみつ = 生成器.つぎせいすう(最大) + 最小
    // …残りは不変（19.3 の完全コードと組み合わせて使う）
}
```

**②「もう一局するか」を関数へ抽出**（メインはフローだけに）：

```jc
関数 もういっきょく(): しんぎ {
    ひょうじ("もう一局？（終了 と入力すれば終了。それ以外のキーで続行）")
    かえす よみこむ() != "終了"
}

メイン() {
    ひょうじ("== 数当てゲーム ==")
    あいだ (真) {
        いっきょく()          // 19.3 の完全コードと組み合わせて使う（断片）
        もし (!もういっきょく()) { ぬける }
    }
    ひょうじ("さようなら！")
}
```

**③ 無効入力の促し文を定数へ抽出**（文言を一箇所で管理）。

> リファクタリングの鉄則：**リファクタリングのたびにテストを一回走らせる**。テストが全部緑 = 振る舞いが変わっていない = リファクタリング成功。

## 19.7 発展の挑戦

1. **難易度の変更**：数当てを「1 から 1000」に変えて、最大何回必要か見よう（ヒント：二分。2¹⁰=1024）；
2. **戦績の集計**：`リスト` で毎局の回数を記録し、ゲーム終了後に「平均 X 回で正解」と表示；
3. **コンピュータがあなたの数を当てる**：役割を交代——あなたが数を思い浮かべ、コンピュータが二分法で当てる（ヒント：`あいだ (真)` + `よみこむ` で「大きい」「小さい」「正解」に答える。第 17 章の二分思想の実戦）；
4. **回数を制限**：10 回で当てられなければ負け（ヒント：`かいすう >= 10` で `ぬける` して答えを明かす）；
5. **究極の挑戦**：「はんだん」の戻り値を `文字列` から `列挙 けっか { 小さい | 大きい | 正解 }` に変えて、プロジェクト全体をリファクタリング——列挙 + 網羅性検査がコードをどう安全にするかを体感しよう（第 13 章）。

## 19.8 プロジェクトの変種：役割交代——今回はコンピュータが当てる

19.1 の主線は「コンピュータが出題し、人が当てる」。逆はどうか？——**あなたが 1 から 100 の整数を心に思い浮かべる（口に出さない）。コンピュータが当てる**。あなたは「大きい」「小さい」「正解」を教える。

コンピュータは当てずっぽうではない。**二分法**を使う：毎回真ん中の数を当て、一発で半分の可能性を排除する——50 と当てて「小さい」と言われたら、答えは 51〜100 にあり、50 通りの可能性が半分になる。75 と当てて「大きい」と言われたら、範囲は 51〜74 に縮む……一回ごとに可能性が半分になり、100 個の数は最大 7 回で確定する（2⁷ = 128 ≥ 100）。これがまさに第 17 章の二分探索思想の実戦（19.7 の挑戦 3 の完全実装）：

```jc
メイン() {
    変数 最低 = 1
    変数 最高 = 100
    変数 かいすう = 0
    ひょうじ("1 から 100 の整数を思い浮かべて。私が当てる！")
    あいだ (真) {
        かいすう = かいすう + 1
        おく あて = (最低 + 最高) / 2
        ひょうじ("${かいすう}回目：私の予想は${あて}。大きい、小さい、正解——どれ？")
        おく へんじ = よみこむ()
        もし (へんじ == "大きい") {
            最高 = あて - 1
        } またもし (へんじ == "小さい") {
            最低 = あて + 1
        } またもし (へんじ == "正解") {
            ひょうじ("ははっ、${かいすう}回で当てた！")
            ぬける
        } またもし (へんじ == "終了") {
            ひょうじ("わかった、やめてあげる！")
            ぬける
        } でなければ {
            ひょうじ("入力は：大きい / 小さい / 正解（または「終了」）")
            かいすう = かいすう - 1    // 無効な回答は回数に数えない
        }
    }
}
```

一回の対話を実行（`zhc run` のあと「小さい / 大きい / 正解」を入力）：

```text
1 から 100 の整数を思い浮かべて。私が当てる！
1回目：私の予想は50。大きい、小さい、正解——どれ？
小さい
2回目：私の予想は75。大きい、小さい、正解——どれ？
大きい
3回目：私の予想は62。大きい、小さい、正解——どれ？
正解
ははっ、3回で当てた！
```

**この変種が使っているもの**：`変数`（最低/最高/かいすう は更新が要る）、`あいだ (真)` + `ぬける`（当てるか終了するまで無限ループ）、`もし/またもし`（回答に応じて範囲を狭める）、`よみこむ`（あなたの回答を読む）、数学（二分法 `(最低 + 最高) / 2`）。19.1-19.6 の主線と比べると、乱数と「もう一局」はないが、**戦略**がひとつ増えている——プログラムは筋書き通りに進むだけでなく、「考えて」動く。（19.1 の受け入れ基準と同じく、いつでも「終了」と入力すれば終了できる。）

**変種の挑戦**：

1. 範囲を 1 から 1000 に：最大何回で当てられる？（ヒント：2¹⁰ = 1024）
2. コンピュータが「ミスリード」されたらどうなる：毎回当てる前に「本当のことを言ってね」と表示するようにすると、`かいすう` はどうなる？どう直す？（ヒント：促し文を 1 回目の前に置く。毎回にはしない）
3. 究極の変種：プログラムが「出題者」になって**乱数で数を思い浮かべ**（ランダムモジュールは 19.3 参照）、あなたが「回答者」になる——19.1-19.6 の版とこの変種を「二人プレイ」に合体しよう：一局はあなたが当て、一局はコンピュータが当てる。使った回数が少ない方の勝ち！

## まとめ

- 完全なプロジェクトの流れ：要件（一文 + 受け入れ基準）→ 設計（要件点ごとに知識点が一つ）→ テスト先行（赤-緑-リファクタリング）→ 実装 → デバッグ（五段階法）→ リファクタリング（テストが保険）→ コミットとリリース；
- 数当てゲームで使ったもの：乱数、`オプション` の解析と受け皿、`あいだ (真)` + `ぬける`、純関数、入れ子ループ——**全書知識の最初の総動員**；
- テスト先行が設計をきれいにする：中核ロジックを純関数に書き、対話とロジックを分離する；
- リファクタリングの鉄則：振る舞いを変えず、構造だけを変え、たびにテストを走らせる；
- リリースのチェックリスト：テスト全部緑 → 受け入れ基準を手動検証 → ドキュメント → lint → tag。

## 考えてみよう

2. メインの `あいだ (真)` ループの中に `いっきょく` の `あいだ (真)` が入れ子になっている——この入れ子ループの出口はそれぞれ何か？
