# 第 16 章 プログラミング設計思想

> **この章の学習目標**：これまでの各章の「設計思想」を体系へまとめる——文法は表、思想は裏。倉頡がなぜこう設計されたかを理解すれば、文法は丸暗記の必要がなくなる。
> **この章を読み終えると答えられる問い**：倉頡は三つのどんな仕組みでメモリの災難を根絶した？なぜ `おく` がデフォルトなのか？網羅性検査は何から守ってくれる？

---

## 16.1 プログラミング設計思想とは何か

**定義**：プログラミング設計思想 = 言語設計者が文法の背後で下した**価値のトレードオフ**。個々の文法機能は一つの問いに答えている：「私たちは何を犠牲にし、何と引き換えたのか？」

| 言語機能 | 犠牲 | 引き換え |
|---|---|---|
| `なし`（null）がない（オプション） | 書くときのアンラップが 1 層増える | ヌルポインタの bug が絶滅 |
| デフォルト不変（`おく`） | `変数` を 1 語多く打つ | 意図しない変更・並行の競合が大幅減少 |
| 明示的な `開放`/`上書き` | キーワードを 2 つ多く打つ | 継承関係が明確で制御可能 |
| 網羅性検査 | マッチは全分岐を書かねばならない | 分岐漏れがコンパイル時に露呈 |

**なぜか**：初心者は「どう使う」だけを学ぶ。熟達者は「なぜこう設計されたのか」を問う——後者こそ応用の効く能力の源泉：トレードオフを理解していれば、新しい言語や API に出会ったとき設計意図を自分で推論できる。丸暗記は不要になる。

## 16.2 メモリ安全：null のない世界

**思想**：C/C++ は数十年にわたり**ヌルポインタ**と**ダングリング参照**の二類の bug に苦しめられてきた（セキュリティ脆弱性の大本）。倉頡は「コンパイラは厳格に、プログラマの自由は少しだけ」を選ぶ——エラーを実行時のクラッシュではなくコンパイル期に防ぐ。

**現れ方**：

- **`なし` キーワードがない**：可空性が型システムに入る——`オプション<T>` は `あり(x)` か `なし` のどちらか（第 14 章）；
- **ダングリング参照**：参照のライフサイクルはコンパイラが管理する（所有権/借用検査）。使い終わったメモリは「宙に浮かない」；
- **エラーメッセージが実を結ぶ**：「不変の値に代入できません」「型が一致しません」はみなこの思想が診断に現れた姿。

## 16.3 値型と参照型の分担

**思想**：型は二類に分かれる——**値型**（コピー意味論：整数、構造体、列挙、タプル）と**参照型**（共有意味論：クラス、配列、文字列、インタフェース）。二つの意味論にはそれぞれ適した場面がある。**データ構造が意味論を決めるのであって、呼び出し側が決めるのではない**：

| | 値型 | 参照型 |
|---|---|---|
| 代入 | 全体コピー（別名なし） | 参照の共有（別名あり） |
| 長所 | 予測可能・スレッド安全・意図しない串刺し変更なし | 大きなオブジェクトをコピーしない・多態に必須 |
| 代表 | `構造体`、列挙、タプル | `クラス`、配列、文字列 |

**経験則**：データが小さく独立していれば構造体。多態/共有が必要ならクラス（第 12 章）。コピーの変更は元の値に影響しない——「別名なし」が推論を単純にする：一つの変数は一箇所だけで変更される。

## 16.4 不変デフォルト（`おく` 優先）

**思想**：可変性は bug の主要な源泉（意図しない変更、並行の競合、推論の困難）。倉頡は「不変」をデフォルト値にした——**可変は申請が必要な特権になる**。コードを読むとき `変数` を一瞥すれば、どこが変わり得るかが分かる：

```jc
メイン() {
    おく 構成 = "固定値"       // 不変：読むときにこれが変わらないか心配しなくてよい
    変数 かず = 0            // 可変：ここだけが変わり得る。重点的に注視する
}
```

**現れ方**：`おく` がデフォルト、引数は読み取り専用、構造体のフィールドは `可変` が付いたときだけ変更できる、文字列は不変（第 9/12 章）。

**並行のボーナス**（第 14 章）：不変データは**同期が不要**——並行に変更されず、データ競合もない。並行プログラムではできるだけ `おく` を。本当に共有する可変状態だけが `同期`/アトミックを必要とする。

## 16.5 型推論と強い型付け

**思想**：二派の長所を兼ねる——**動的言語の書き味**（型注釈をあまり書かない）+ **静的言語の安全性**（コンパイル期に全部検査）。設計原則：**推論できるところは書かず、肝心なところには必ず書く**：

```jc
メイン() {
    おく x = 90                // 推論：せいすう
}
関数 二倍(数: せいすう): せいすう { かえす 数 * 2 }   // 引数は注釈必須——インタフェースの契約を明示
```

**現れ方**：ローカル変数と戻り値の型は推論できる。**関数の引数は型注釈が必須**（これはインタフェース契約の一部）。ジェネリック呼び出しは自動インスタンス化（第 15 章）。

## 16.6 多パラダイム融合：式は値

**思想**：全問題を一つのパラダイムで解けるわけではない。倉頡は排他ではなく吸収——ロジックは命令式で、データ処理は関数式で、システムのモデリングは OO で。各パラダイムの長所を取り出す：

```jc
メイン() {
    おく てん = 85
    おく 等級 = もし (てん >= 60) { "合格" } でなければ { "不合格" }   // もし は式：値を持つ
    ひょうじ(等級)

    おく 説明 = マッチ (てん) {                                    // マッチ は式：値を持つ
        場合 x そのなか (x >= 90) => "優秀"
        場合 _ => "その他"
    }
    ひょうじ(説明)
}
```

**現れ方**：`もし`/`マッチ` は式（関数式）でありながら文の書き方（命令式）もサポート。`マッチ` の網羅性検査 + `うつす`/`こす` のチェーン（関数式）+ クラス階層（OO）が併存する。**「式は値」がコードをコンパクトにする**：代入と分岐が一つになり、一時変数が減る。

## 16.7 パターンマッチと網羅性検査

**思想**：`もし` の連鎖は「手動で分岐を管理する」——`でなければ` を 1 つ書き忘れてもコンパイラは黙り、実行時こっそり違う道を歩く。網羅性検査は「分岐の完全性」を**コンパイルエラー**にする——これは倉頡が関数型言語から受け継いだ最強の安全設計の一つ（第 13 章）。

**現れ方**：列挙/オプション/タプルのマッチは網羅（または `_` の受け皿）が必須。`場合 あり(名前)` は判定と分解を同時に行う。新しい列挙メンバを足すと、すべてのマッチ箇所がコンパイルエラーになる——**新しい状況への対処を強制する**（拡張性の安全網）。

## 16.8 明示は暗示に勝る：インタフェース契約の可視化

**思想**：「間違え得る箇所」をすべて**明示的なコンパイル期検査**にする。代償は語をいくつか多く打つこと。収穫は bug の一類が消えること。倉頡の明示設計リスト：

| 明示のマーク | 防ぐエラー |
|---|---|
| `開放` があって初めて継承可能 | 意図しない継承がカプセル化を壊す |
| `上書き` があって初めて上書き可能 | メソッド名の書き間違いが新メソッドになる |
| `可変` があって初めて構造体自身を変更 | コピーがこっそり変わる |
| `として` があって初めてダウンキャスト | 型の取り違え |
| `そのなか T <: ひかくかのう` | ジェネリックコードが存在しないメソッドを呼ぶ |
| 引数の型注釈必須 | インタフェース契約があいまい |

**思想の核心**：**デフォルト閉鎖、デフォルト不変、デフォルト明示**——三つの「デフォルト」が特権を申請制にする。コードを読むとき、明示のマークを一瞥すれば「どこで変更が許され、どこで拡張が許されるか」が分かる。

## 16.9 拡張：開かれた世界の設計

**思想**：古典 OO の「クラスを変更する」には二つの痛点がある：変更する権限がない（標準ライブラリ/サードパーティ）と、変更すれば全員に影響する（脆い）。`拡張` は「振る舞いを足す」を**外付け式**の操作にする——各モジュールが自分が関心を持つ型にメソッドを掛け、互いに干渉しない：

```jc
拡張 せいすう {
    おおやけ 関数 二倍(): せいすう { かえす これ * 2 }
}

メイン() {
    ひょうじ(21.二倍())        // 42（拡張メソッドをネイティブメソッドのように呼べる）
}
```

**現れ方**：文字列/コレクションの方言メソッド名（`けずる`/`わける` など）の多くは拡張の仕組みに依存して実装されている。**組み合わせは継承に勝る**：組み合わせで表現できる has-a の関係に、継承を無理やり作らない。

## 16.10 エラー処理の哲学

**思想**：エラー処理は**設計判断**であって文法ではない——失敗の場面ごとにまず分類する（第 14 章）：

- **予期した失敗**（入力、見つからない、範囲外）→ `オプション`：失敗は戻り値の一部。呼び出し側が処理を強いられる；
- **想定外のエラー**（bug、環境）→ 例外：呼び出しスタックを自動で巻き上がり、能力のある者が捕捉する；
- **Fail fast**：`なければれいがい()`、事前検査——エラーは早く露呈するほど直しやすい。エラーを飲み込むのが最も危険なコード；
- **例外を制御フローに使わない**：性能も読みやすさも悪い。

## 16.11 宣言的データ処理

**思想**：「走査 + 条件判断 + 収集」を 1 ステップに圧縮する——**宣言的**コードは「何をするか」を言い（不合格をこす）、**命令的**コードは「どうやるか」を言う（リストを作り、ループし、判断し、追加する）。意図を直接言い、読者が翻訳する必要がない：

```jc
いれる 標準コレクション.*
メイン() {
    変数 せいせき = リスト<せいすう>()
    せいせき.くわえる(95); せいせき.くわえる(45); せいせき.くわえる(70)
    おく ごうかく = せいせき |> こす({ x => x >= 60 }) |> はいれつあつめ   // 宣言的
    ひょうじ(ごうかく.ながさ)       // 2
}
```

**付随する思想**：**遅延評価**——`うつす`/`こす` はイテレータを返し、消費される（`はいれつあつめ`）ときにはじめて本当に計算する。**元のコンテナは変わらない**——関数式スタイルでは元データは「入力」であり、こっそり書き換えられない。

## 16.12 メタプログラミング：コンパイル期の評価

**思想**：「毎回の実行で繰り返す仕事」を「コンパイル時に 1 回」へ前倒しする——マクロはコンパイル期に実行され、実行時には展開結果だけが残る。**ゼロオーバーヘッド**。マクロのクラッシュ = コンパイルエラー（良いこと）。エラーは最も早い時点で露呈する（第 15 章）。

**三つの安全設計**（C プリプロセッサのテキスト置換との対比）：

- **衛生的マクロ**：呼び出し側の変数をうっかり捕捉しない；
- **型付き**：入力も出力も `Tokens`；
- **IO なし**：マクロはファイルを読めず、ネットワークにも触れない——ビルドの再現性を保証する。

**時期の判断**：「重複コード」の 9 割は関数/ジェネリクスで消せる。**コードそのものの操作**が必要なときにだけマクロの出番——マクロは最後の手段であって第一の選択ではない。

## 16.13 zhc 方言の設計思想

**① 用語の母語化（日本語がそのままコード）**：方言は「ドキュメントの翻訳」ではない——言語そのものを母語へ翻訳する。キーワード、標準ライブラリ、エラーメッセージがすべて母語になる。プログラミングの認知負担は二層に分かれる：**アルゴリズム思考**（もともと母語で考える）と**言語の敷居**（英語のキーワード）——方言は第二層を取り除く。「母語で考え、母語で表現する」。

**② 診断は教学である**：コンパイラのエラーは学習の第一現場——初心者の 7 割の時間はコンパイラとの対話に費やされる。母語の診断が「エラーメッセージ」を「教材」に変える：どう間違えたか（💡）、どう直すか（修正例）——これは zhc が公式コンパイラに対して持つ**付加価値の層**。

**③ 転訳は辞書引きである**：方言は新しい言語ではなく「**語表駆動の書き換え規則**」——辞書の置換 + 文脈の保護（文字列を誤って変えない、宣言名を免除する、挿入保護）。この設計を理解すれば、なぜ語表を変えると新しい方言が作れるのかが分かる。

**④ 言語パックは拡張可能（方言は設定である）**：方言の全体は一組の**データファイル**（語表/メッセージ表）であって、書き込まれたコードのロジックではない——**転訳エンジンと言語パックは疎結合**：言語パックは独立して進化でき、検証でき（`mapping check`）、拡張できる（カスタムエラーコード）。語表を取り替えれば新しい方言になる——これが「言語非依存」の土台。

## まとめ

- プログラミング設計思想 = 文法の背後にある価値のトレードオフ：少しの便利さを犠牲に、ある類の bug を絶滅させる；
- 倉頡の四つの礎石：メモリ安全（なし なし）、不変デフォルト、明示の契約、網羅性検査；
- 多パラダイム融合：ロジックは命令式、データは関数式、システムは OO。各パラダイムの長所を取り出す；
- エラー処理の哲学：予期した失敗はオプション、想定外は例外、素早く失敗する；
- zhc の四つの思想：母語化、診断は教学、転訳は辞書引き、言語パックは拡張可能。
