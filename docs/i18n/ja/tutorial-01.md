# 第 1 章 プログラミングって何？

> **この章の目標**
> - 「プログラミング」が実際に何をしているのかを知る——レシピを書くこと；
> - 道具を知る：倉頡（Cangjie）+ zhc。母語のコードがどうやってコンピューターに伝わるのかを理解する；
> - 環境構築を自分の手でやる：SDK のインストール、環境変数の設定、zhc のビルド、そして**動作確認まで**。
>
> **この章を読み終えると答えられる**：コンピューターはなぜ「おバカ」なの？プログラムとは？通訳者は誰？私の `zhc` はどうやって段階的にインストールされたの？

---

## 1.1 コンピューターは賢いけれど、とてもバカ

コンピューターは一瞬で数億回の足し算ができます。しかし**人間の言葉は理解できません**。「ゲームを作って」と叫んでも、ポカンとされるだけです。

コンピューターが理解できる言語はただ一つ、しかも記号が `0` と `1` の二つだけという、とても簡単な言語です。これは昔の戦場で使われたのろしと同じ——**ついている（1）** か **ついていない（0）** か。この二つの状態だけでメッセージを伝えます。

では問題です：こんなバカなコンピューターに、どうやって命令を伝えればいいのでしょう？

## 1.2 プログラミング = レシピを書くこと

料理をしたことのない友達に「トマトと卵の炒め物」の作り方を教える場面を想像してください。あなたはどう書きますか？

```
手順1：卵を二つボウルに割り入れ、よく混ぜる
手順2：トマトを一口大に切る
手順3：フライパンに油を引き、熱する
手順4：卵を入れ、炒めて取り出す
手順5：トマトを入れ、汁が出るまで炒め、卵を戻し、塩を加える
手順6：皿に盛る
```

**プログラミングとはまさにこれ**：コンピューターにしてほしいことを、一歩ずつはっきりと、「コンピューターの読めるレシピ」として書き下すことです。このレシピを**プログラム**（program）と呼びます。レシピを書く人を**プログラマー**と呼びます——そう、あなたのことです。

## 1.3 プログラミング言語 = 通訳者

コンピューターは `0` と `1` しか分かりません。それなら最初から `0` と `1` でプログラムを書けばいい？それはモールス信号で作文を書くようなもので、とても苦しいことです。

そこで賢い人々が**プログラミング言語**を発明しました：人間の言葉に近い「中間言語」です。コンピューターは**コンパイラ**（通訳者のようなもの）を通じて、このプログラミング言語を `0` と `1` に翻訳してもらいます。

世界にはたくさんのプログラミング言語があります。ほとんどは英語ベースですが——

## 1.4 母語でもプログラミングできる

**倉頡**（Cangjie）は、中国の**ファーウェイ**が開発した、全シナリオ向けスマートプログラミングの新世代言語です。そして **zhc**（倉頡方言フレームワーク）はそれをさらに推し進めます：キーワードも、関数名も、エラー表示も、**全部あなたの母語で書ける**！

| ほかの言語なら辞書が必要 | 私たちは zhc でこう書く |
|---|---|
| プログラムの入口を暗記 | `メイン()` |
| 表示関数を暗記 | `ひょうじ("こんにちは")` |
| 不変の値を宣言する言葉を暗記 | `おく x = 1` |
| 条件分岐の言葉を暗記 | `もし ... でなければ ...` |

**コードを書くときに英和辞典を引く必要がありません。** エラーも日本語で表示され、「💡 ヒント」と「修正例」付きです——この本の一番の自信作です。

> **用語ミニ辞書**
> - **プログラム**：コンピューターに読ませる「レシピ」
> - **コード**：プログラムの別名。「作文」と「文章」の関係と同じ
> - **実行（ラン）**：コンピューターにプログラムを動かしてもらうこと
> - **コンパイラ**：母語のコードをコンピューターの分かる `0` と `1` に翻訳する通訳者
> - **zhc**：方言フレームワーク——方言コードを標準倉頡に翻訳して（コンパイラへ渡し）、コンパイラの英語エラーを母語に翻訳して返す（私たちへ）

## 1.5 道具をインストールする

インストールするものは二つです：

1. **公式倉頡 SDK**：コンパイラ `cjc` とパッケージマネージャ `cjpm` を同梱（通訳者本人）；
2. **zhc**：方言フレームワーク（母語 ↔ 倉頡の往復翻訳を担当）。

以下の 7 ステップはすべて「実機で検証済み」の手順です。各ステップに**検証方法**（終わったら何が見えるか）が付いています。そのまま進めれば、道具が揃います。

> 環境要件：Linux x86_64（64 ビット）、インターネット接続可。Windows/macOS の方は本章 1.5 ステップ 7 の後のトラブルシューティング表を先に読むか、オフライン配布パッケージ（SDK 不要）を使ってください。

### ステップ 0：環境の確認（3 分）

**ターミナル**（Linux の端末）を開き、1 行ずつ入力して確認します：

```bash
uname -m          # 期待する出力：x86_64
git --version     # 期待する出力：git version 2.x（無ければ：sudo apt install -y git）
```

> 「ターミナル」が分からない？コンピューターの「コマンド窓」です——文字を打ち込むとコンピューターが働いてくれる窓。以後のステップはすべてここで行います。

### ステップ 1：公式倉頡 SDK のインストール（10 分）

ファーウェイ倉頡の公式チャンネルから Linux x86_64 の SDK 圧縮ファイルをダウンロードします（コンパイラ・ランタイム・標準ライブラリが一つにまとまっています）。

`~/ruanj` ディレクトリに解凍し、フォルダ名を統一して `cangjie` にします（この後のパスは全部これに依存——名前を揃えるのが一番楽）：

```bash
mkdir -p ~/ruanj
tar -xzf ダウンロードした倉頡SDKの圧縮ファイル.tar.gz -C ~/ruanj
mv ~/ruanj/解凍したディレクトリ名 ~/ruanj/cangjie    # 解凍ディレクトリを cangjie に改名
```

解凍後、SDK が次の形になっていることを確認します（**この後のパスは全部これに依存**）：

```
~/ruanj/cangjie/
├── bin/
│   └── cjc                     # コンパイラ（通訳者）
├── tools/bin/
│   └── cjpm                    # パッケージマネージャ（部品の追加・ビルド）
├── runtime/lib/linux_x86_64_cjnative/
│   └── libcangjie-runtime.so   # ランタイムライブラリ（倉頡プログラムの実行に必須）
└── tools/lib/                  # ビルド時ライブラリ（コンパイル時に必要）
```

> ⚠️ よくある誤解：`cjc` は `bin/` の下、`cjpm` は `tools/bin/` の下にあります——**両方とも** PATH に通します（次のステップでまとめて設定）。

### ステップ 2：環境変数の設定（3 分）

環境変数はコンピューターの「アドレス帳」——道具の在りかをコンピューターに教えます。次の 3 行を `~/.bashrc`（ターミナルを開くたびに読まれる設定ファイル）に追加します：

```bash
cat >> ~/.bashrc <<'EOF'

# ---- 倉頡 SDK ----
export CANGJIE_HOME="$HOME/ruanj/cangjie"
export PATH="$CANGJIE_HOME/bin:$CANGJIE_HOME/tools/bin:$PATH"
export LD_LIBRARY_PATH="$CANGJIE_HOME/runtime/lib/linux_x86_64_cjnative:$CANGJIE_HOME/tools/lib:${LD_LIBRARY_PATH:-}"
EOF
source ~/.bashrc
```

この 3 行はそれぞれ何をしているのか（**なぜこう書くのか**）：

| 変数 | 役割 | 設定しないとどうなる |
|---|---|---|
| `CANGJIE_HOME` | SDK の場所を記憶（ほかのツールが尋ねてくる） | 一部のツールが SDK を見つけられない |
| `PATH` | `cjc`・`cjpm` コマンドを直接打てるようにする | `cjc: command not found`（コマンドが見つからない） |
| `LD_LIBRARY_PATH` | ランタイムライブラリ `.so` を探せるようにする | `error while loading shared libraries` が出る |

### ステップ 3：SDK の検証（1 分）

```bash
cjc --version
# 期待する出力：Cangjie Compiler: 1.0.5 (cjnative)

cjpm --version
# 期待する出力：Cangjie Package Manager: 1.0.5
```

バージョン番号が見えたら SDK はインストール完了です！（バージョン ≥ 1.0.5 なら OK）

### ステップ 4：zhc のソースを取得する（2 分）

zhc はオープンソースプロジェクトです。`git` でソースをローカルにダウンロードします：

```bash
git clone <このプロジェクトのリポジトリURL> ~/code/zwCangjie
cd ~/code/zwCangjie/zhc
```

ソースの中に不思議なディレクトリ `lang-packs/` があります——**日本語の単語表そのもの**です：

```
zhc/lang-packs/ja/
├── keywords.toml        # キーワード表：1 行ごとに「方言語 → 公式語」
├── stdlib.toml          # 標準ライブラリ別名表：方言 API 名 → 公式 API 名
├── module_paths.toml    # モジュールパス対応：方言パス名 → 公式パス
├── errors.toml          # エラーメッセージ：診断コードの日本語テンプレート
└── ui.toml              # ツールの画面文言
```

> 💡 **ひみつ**：zhc の「母語対応」はすべてこれらの**データファイル**にあり、コードに書き込まれていません。単語表を入れ替えるだけで新しい方言が生まれます——ロシア語の単語表ならロシア語の倉頡が書けます（プロジェクトに実演パックあり）。あなたが学ぶのはこの「日本語方言」です。

### ステップ 5：zhc 本体のビルド（3〜10 分）

`zhc/` ディレクトリで実行します（初回は依存関係のコンパイルがあるので気長に待ちます）：

```bash
cjpm build
```

成功の目印——成果物が現れて実行可能になっていること：

```bash
ls -l target/release/bin/main
# 期待する出力：-rwxr-xr-x ... target/release/bin/main
```

ビルド成果物の名前は `main`。これが zhc 本体です。`~/.local/bin` にコピーして正式な名前 `zhc` を付け、PATH に通します：

```bash
mkdir -p ~/.local/bin
cp target/release/bin/main ~/.local/bin/zhc
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
```

### ステップ 6：zhc に言語パックを見つけさせる（2 分）

zhc は次の順序で言語パックを探します（どれか一つが成立すれば OK）：環境変数 `ZHC_LANG_PACKS` → カレントディレクトリ `./lang-packs/` → 実行ファイルの隣の `lang-packs/` → ユーザーディレクトリ `~/.zhc/lang-packs/`。

ソースビルドでは 1 番目（明示的で、実行ディレクトリに依存しない）を推奨します：

```bash
echo 'export ZHC_LANG_PACKS="$HOME/code/zwCangjie/zhc"' >> ~/.bashrc
source ~/.bashrc
```

### ステップ 7：インストールの検証（1 分）

```bash
zhc --help
```

`Usage:` の行（例：`zhc init … create a project skeleton`）が見えたら成功です。なお `zhc --help` の usage は常に英語ですが、`zhc run` などのメッセージは `ZHCLANG` の言語に従います（日本語 UI を試すには `ZHCLANG=ja` を設定してください）。実際にプログラムを一つ動かしてみましょう（同梱の日本語方言サンプル）：

```bash
cd ~/code/zwCangjie/zhc/examples
zhc run ja-hello.jc
```

期待する出力（1 行目のメッセージは英語表示です——日本語パックは未翻訳の文言を英語にフォールバックします）：

```
✅ Compilation OK: replaced 7 dialect identifier(s).
こんにちは、日本！
数: 42
```

🎉 **おめでとうございます！母語（日本語）倉頡の環境が整いました！** 第 2 章から、いよいよプログラムを書いていきます。

> **詰まったら？ミニトラブルシューティング表**
>
> | 症状 | 原因 | 解決 |
> |---|---|---|
> | `cjc: command not found` | PATH の設定ミス | ステップ 2 をやり直し、`source ~/.bashrc` が実行されているか確認 |
> | `error while loading shared libraries` | LD_LIBRARY_PATH の設定ミス | ステップ 2 の 3 行目を確認、SDK パスが正しいかどうか |
> | `uname -m` が x86_64 でない | アーキテクチャ非対応 | 64 ビット OS に切り替えるか、オフライン配布パッケージ方式を使用 |
> | `cjpm build` が依存エラー | ネットワーク/バージョン問題 | ネットワークを確認してもう一度；ダメなら README か質問を |
> | `zhc` が言語パックを見つけられない | ZHC_LANG_PACKS 未設定 | ステップ 6 をやり直し、`lang-packs/` を含むディレクトリを指しているか確認 |

## 1.6 やってみよう

1. ターミナルを開いて `zhc --help` を実行し、出力の中から知っているサブコマンド（`run`、`check` など）を書き出してみましょう；
2. `~/code/zwCangjie/zhc/lang-packs/ja/keywords.toml` を開いて、「方言語 → 公式語」の対応を何行か眺め、単語表の形を感じ取りましょう；
3. `examples` ディレクトリで `zhc run ja-hello.jc` をもう一度実行し、`ja-hello.jc` の中の文字列（たとえば「こんにちは、日本！」）を自分の名前に書き換えて、もう一度実行してみましょう——**初めてコードを書き換えました。あなたはもうプログラマーです**。

## ✳ プログラミング思想の小話：大きな問題を小さなステップに分解する

「プログラミング = レシピを書くこと」というたとえの背後には、プログラミングで最も重要な思想があります：**分解**です。

- トマト卵炒めが作れない？大丈夫、6 つのステップに分ければ、それぞれはとても簡単です；
- ゲームが書けない？大丈夫、「画面を出す → キー入力を受け取る → 計算する → 画面を更新する」に分解して、それぞれの小さなステップをさらに分解していきます。

**どんな複雑な問題も、一歩一歩が簡単で間違えようがないところまで分解すれば、必ずやり遂げられます。** これはプログラマーがすべての問題を解く最初の手筋です——これからコードを書いていて難題にぶつかったら、まず自分に問いかけてください：もっと小さく分解できないか？

## 🍳 日常アルゴリズム小話：朝の登校 = 順次実行

プログラムの最も基本的な構造を**順次実行**と呼びます：上から下へ、一歩終わったら次の一歩。あなたの毎朝は、まさに一つのプログラムです：

```
1. 起きる
2. 歯を磨く
3. 朝ごはんを食べる
4. ランドセルを背負う
5. 家を出て学校へ行く
```

この「レシピ」にはいくつかの特徴があります——順序がある、入れ替えられない、一歩につき一つのことだけをする。**コンピューターがプログラムを実行するのも同じ：一文ずつ、まっすぐに。** 第 2 章では、プログラムの中の順次実行がどんな形をしているかを見ていきます。

## まとめ

- コンピューターは賢くてバカ：`0` と `1` しか分からないので、「レシピ」が必要；
- プログラム = コンピューターに書いて渡すレシピ。プログラミング言語 + コンパイラ（通訳者）が、レシピを人間の言葉のように書けるようにしてくれる；
- 倉頡は中国発のプログラミング言語。**zhc ならキーワードも関数名もエラー表示も母語で完結**；
- 環境構築の 7 ステップ：環境確認 → SDK インストール → 環境変数設定 → SDK 検証 → ソース取得 → zhc ビルド → 動作検証；
- プログラミングの第一思想：**大きな問題を小さなステップに分解する**（分解）。

4. 考えよう：ステップ 2 ではなぜ環境変数を `~/.bashrc` に書いたのか、毎回手で打つのはダメなのか？（ヒント：レシピの繰り返し実行）
