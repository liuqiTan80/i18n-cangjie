# 第 15 章 ジェネリクス・インタフェース・マクロ

> **この章の学習目標**：「汎用コードを書く」二大メカニズム——ジェネリクス（型のパラメータ化 + そのなか 制約）とマクロ（コンパイル時コード変換）を身につけ、`@テスト`/`@期待` でユニットテストを書き、`zhc expand` でマクロ展開を観察する。
> **この章を読み終えると答えられる問い**：ジェネリクスとマクロはそれぞれ何を解決する？`$(...)` と `${...}` は何が違う？なぜ二段階コンパイルなのか？

---

## 15.1 ジェネリック関数：1 つの関数、すべての型

**定義**：ジェネリクス = **型のパラメータ化**——1 つの関数を書けばどんな型にも使える（型ごとにコピーを量産しなくてよい）。`<T>` が型パラメータ。呼び出し時に自動でインスタンス化される。

**日本語の書き方**：

```jc
関数 さいしょ<T>(データ: はいれつ<T>): T {
    かえす データ[0]
}

メイン() {
    ひょうじ(さいしょ([1, 2, 3]))          // 1（T = せいすう と推論）
    ひょうじ(さいしょ(["あ", "い"]))       // あ（T = 文字列 と推論）
}
```

**注意事項**：

- 型パラメータは関数名の後ろ `<T>`。**大文字始まり**が慣例（`T`、`K`、`V`）；
- 呼び出しではふつう型パラメータを書かない——コンパイラが実引数から**自動推論**する（`さいしょ([1, 2, 3])`）；
- ジェネリクスは**コンパイル時**の仕組み：実行時にはジェネリクスはない（具象型ごとに 1 セットのコードが生成される）——実行時オーバーヘッドはゼロ。

## 15.2 ジェネリック型：コンテナの土台

**定義**：ジェネリクスは関数だけのものではない——**型**もパラメータ化できる：`リスト<T>`、`マップ<K, V>`、`オプション<T>` はみなジェネリック型。君はもう使っている！

**日本語の書き方**：

```jc
いれる 標準コレクション.{リスト}

構造体 はこ<T> {
    おおやけ 変数 なかみ: T
    初期化(なかみ: T) { これ.なかみ = なかみ }
}

メイン() {
    おく 数値箱 = はこ<せいすう>(42)
    おく 文字箱 = はこ<文字列>("倉頡")
    ひょうじ(数値箱.なかみ)    // 42
    ひょうじ(文字箱.なかみ)    // 倉頡

    変数 めいぼ = リスト<文字列>()
    めいぼ.くわえる("あ")
    ひょうじ(めいぼ[0])        // あ
}
```

**注意事項**：空のコンテナには**型パラメータの明記が必須**（`リスト<文字列>()`——書かなければコンパイラは何を入れるのか分からない）。ジェネリック型の名前は大文字が慣例（`はこ` に大文字小文字はないが、書く内容の約束は明記しておく）。

## 15.3 そのなか（制約）：ジェネリクスの境界

**定義**：ジェネリクスも自由すぎては困る——`<T>` に `.ひかく` メソッドを呼んでもコンパイラは認めない（T はどんな型かもしれない）。**そのなか**（制約）は T が満たすべき条件を限定する：`そのなか T <: ひかくかのう<T>`。

**日本語の書き方**：

```jc
関数 さいだいち<T>(データ: はいれつ<T>): T そのなか T <: ひかくかのう<T> {
    変数 さいだい = データ[0]
    それぞれ (こうもく in データ) {
        もし (こうもく > さいだい) { さいだい = こうもく }
    }
    かえす さいだい
}

メイン() {
    ひょうじ(さいだいち([3, 7, 2, 9]))          // 9
    ひょうじ(さいだいち(["あ", "い", "う"]))    // う（文字列も比較できる）
}
```

**注意事項**：

- `そのなか T <: ひかくかのう<T>`——T は `ひかくかのう` インタフェースを実装した型でなければならない。**ジェネリックインタフェースを制約に使うときは型パラメータを添える**（`ひかくかのう<T>` と書く。`ひかくかのう` だけではダメ）；
- 制約は**戻り値型の後、関数本体の前**に書く：`関数 名<T>(引数): 戻り値型 そのなか T <: ひかくかのう<T> { ... }`——戻り値型が先；
- 制約のないジェネリクスは「入れて、出す」しかできない。メソッドを呼びたければ制約が必要（制約は「能力リスト」。第 12 章のインタフェース思想のジェネリクス版）。

> 💡 実測のヒント：`そのなか` 節の形は `そのなか T <: ひかくかのう<T>`。`ひかくかのう` は言語パック収録の型語。必ず `ひかくかのう<T>` の形で制約を書くこと——そうして初めて `>` などの比較演算子が許される。

## 15.4 マクロとは：コンパイル時に実行されるコード変換器

**定義**：マクロは**コンパイル時コード変換器**——コードの token を食べて、コードの token を吐く。呼び出しは `@マクロ名(引数)`。普通の関数は（実行時の）**値**しか操作できないが、マクロは**コードそのもの**（コンパイル時）を操作できる。

**マクロだけが関数にできない三つのこと**：

1. **構文糖の再発明**：繰り返しパターン（ログ記録、時間計測）をマクロ呼び出しにパッケージする；
2. **コンパイル時検査**：パターンをコンパイル時に検証する（例：DSL の文法チェック）；
3. **性能**：展開はコンパイル時に完了。**実行時オーバーヘッドはゼロ**。

**注意事項**：倉頡のマクロは**衛生的マクロ**（呼び出し側の変数をうっかり捕捉しない）+ **型付き**（入力も出力もコード token の流れ）——C プリプロセッサのテキスト置換よりずっと安全。マクロ呼び出しは `@` で始まる。マクロ名は**日本語でもよい**。マクロ展開のエラーはコンパイル時に報告される。

## 15.5 マクロパッケージとマクロ定義

> ⚠️ **全書唯一の公式文法ゾーン**：マクロパッケージのソース（この節と 15.6-15.8 の `macro package` コード）は**必ず公式倉頡文法で書く**——マクロパッケージの `.cj` ファイルは方言転訳を通らない。これは倉頡コンパイラのハードな制約で、中の英語の語（`macro package`/`import`/`Tokens` など）は漏れではない。**方言側（`.jc`）のコードは全書を通して日本語のまま**。マクロパッケージのこの一箇所だけが例外。

**定義**：マクロは必ず**マクロパッケージ**の中に定義する——ソース**先頭行**に `macro package パッケージ名`。マクロパッケージはマクロだけを公開する。マクロパッケージの中は**公式倉頡文法で書く**（`.cj` ファイルは方言転訳を通らない）。

**日本語の書き方**（マクロパッケージファイル `define/define.cj`）：

```cangjie
// define/define.cj —— マクロパッケージのソース（中は公式倉頡文法。方言転訳は通らない）
macro package define
import std.ast.*

public macro デバッグログ(input: Tokens): Tokens {
    let 名前 = input.toString()
    return quote(
        println($(名前))
    )
}
```

**要点（倉頡 1.0 のマクロ規則、1.0.5 実測）**：

- 先頭行 `macro package <パッケージ名>`（**公式文法**——マクロパッケージの `.cj` ファイルは方言転訳を通らない。`マクロパッケージ`/`引用` と書くとコンパイルエラー）；
- 必ず `import std.ast.*`——`Tokens` 型は `std.ast` パッケージ由来（`std.macro` は存在しない）；
- `public macro 名前(input: Tokens): Tokens`——引数も戻り値も必ず `Tokens`。マクロ名は**日本語でもよい**；
- マクロパッケージは**独立したコンパイル単位**：先にマクロライブラリへコンパイルし、メインプログラムのコンパイル時に展開する——マクロはプロジェクトを越えて配布できる。

## 15.6 quote と挿入：コードを書くようにコードを書く

**定義**：`quote(...)`（引用）で**コードを書くようにコードを書く**。`$(式)` は**コード位置の挿入**——変数の値/子コードの token をテンプレートに埋め込む。

**二つの挿入の効果はまったく違う**：

| 書き方 | 効果 | 例 |
|---|---|---|
| `$(input.toString())` | **文字列リテラル**を挿入 | `println("x + 1")`——式の**テキスト**を表示 |
| `$(input)` | **コード token** を直接埋め込む | `if ($(input) == 0)`——**式のまま**保たれる |

**注意事項**：`$()` は**コード位置だけで有効**——文字列リテラルの中では置換されない。`$(input.toString())` が挿入するのは文字列リテラルであって、その中はさらに置換されない——挿入はコード位置でのみ起きる。区別しよう：**`$()` はコード挿入（マクロ）、`${}` は文字列挿入（第 10 章）**——別物。

## 15.7 二段階コンパイルと zhc expand

**定義**：マクロパッケージとメインプログラムは二段階でコンパイルする——これはマクロの「独立コンパイル単位」設計がビルドに現れた姿。

**二段階コンパイルの流れ（1.0.5 実測）**：

```bash
zhc eject main.jc                           # ① 方言 → 公式ソース（main.cj）
cjc define/define.cj --compile-macro       # ② マクロパッケージをコンパイル → define.cjo + lib-macro_define.so
cjc main.cj -o main                        # ③ メインプログラムをコンパイル（import define.* でマクロが自動展開）
./main                                     # 実行
```

> 実測（1.0.5）：`zhc run` はマクロパッケージに**非対応**。日常の展開検証は `zhc expand main.jc --macro-pkg define/`（二段階コンパイルを自動で済ませる。15.8 参照）。あるいは上の 3 ステップを手で実行する。

## 15.8 マクロ展開の教学ビュー：zhc expand

**定義**：`zhc expand` で展開前/後の対照が見られる（公式 + 母語への逆転ビュー。位置マッピングは方言の座標に復元される）——マクロの挙動を学ぶ最高の道具：**先に展開結果を予想してから、ビューで検証**しよう。

**日本語の書き方**：

```bash
zhc expand main.jc --macro-pkg define/
```

```
═══ zhc expand：マクロ展開の教学ビュー ═══
マクロパッケージ：define/（define）

[展開前] main.jc:4
      @デバッグログ(x + y)
[展開後] 公式（main.cj）
      /* 4.1 */println("x + y")
[展開後] 方言（逆転訳）
      /* 4.1 */ひょうじ("x + y")
```

**注意事項**：行番号コメント（`/* 4.1 */`）は**方言ソースの座標**に対応。マクロ展開後のエラー位置はソースマッピングでマクロ呼び出しの場所に復元される。

## 15.9 派生マクロ：ボイラープレート実装の自動生成

**定義**：型に `@導出(ひとしい, ひかく)` と付けると、コンパイラが `ひとしい`/`ひかく`/`ハッシュ` などのメソッドを自動生成する——構造体のこれらの実装は**機械的で繰り返し**（フィールドを順番に比較する）。手書きは長くて間違いやすい。派生マクロは「設定より規約」の典型。

**日本語の書き方**：

```cangjie
// 文法のスケッチ（@導出 はシステムマクロ。使うときはマクロライブラリを先にコンパイルしておく）
構造体 学生 @導出(ひとしい) {
    おおやけ 変数 名前: 文字列
}
```

**注意事項**：派生の条件——フィールドの型が派生する操作をサポートしていること（`ひかく` を派生するなら全フィールドが比較可能でなければならない）。方言の `導出` → 公式の `Derive`。派生マクロと手書き実装は**どちらか一方**（両方書くと衝突エラー）。派生マクロにはマクロライブラリの先行コンパイルが必要（二段階コンパイル）。

## 15.10 システムマクロ：@テスト と @期待

**定義**：倉頡の標準ライブラリはテストフレームワークを内蔵する（`std.unittest`）——`@テスト` がテスト関数をマークし、`@期待` がアサーション。

**日本語の書き方**：

```jc
いれる 標準テストマクロ.*
いれる 標準テスト.*

関数 たす(あ: せいすう, い: せいすう): せいすう { かえす あ + い }

@テスト
おおやけ 関数 たす正しい() {
    @期待(たす(2, 3), 5)   // 式の結果が 5 になることを期待
}
```

**要点（1.0.5 実測）**：

- **ワイルドカード import は二つとも書く**：`標準テストマクロ`（テストフレームワークのマクロ本体）と `標準テスト`（アサーションなどの実行時型）。片方欠けてもダメ；
- `@期待(実際の値, 期待値)` マクロは完全なアサーションコードへ展開され、失敗時には両側の値を示す；
- `@テスト` がマークした関数はフレームワークが自動収集して実行する。手動呼び出しは不要。

プロジェクトルートで全方言テストを一括実行：

```bash
zhc test
```

```
[ 通過 ] テスト：たす正しい
集計：合計 1
    通過： 1, スキップ： 0, エラー： 0
    失敗： 0
```

（実行時の文言は zhc 側の表示形式による。上は zh 教程と同じ書式の例）

## ✳ 設計思想

**① メタプログラミングの順番：まず関数、次にジェネリクス、最後にマクロ**。「重複コード」の 9 割は関数/ジェネリクスで消せる。**コードそのものを操作したい**とき（式のテキストを手に入れる、文法構造を生成する）にだけマクロの出番。マクロは最後の手段であって最初の選択ではない——読みやすさを犠牲にして表現力を得る道具。

**② コンパイル時 vs 実行時**：マクロは「毎回の実行で繰り返す仕事」を「コンパイル時に 1 回」へ前倒しする——実行時オーバーヘッドはゼロ。コンパイル時に決められることは、絶対に実行時まで引き延ばさない。マクロのクラッシュ = コンパイルエラー（良いこと）——エラーは最も早い時点で露呈する。

**③ 制約は契約**：`そのなか T <: ひかくかのう<T>` はジェネリクスの「能力リスト」——ジェネリックコードが呼べるメソッドは制約が決める。これはインタフェース（第 12 章）と同じ思想のもう一つの顔：**抽象に向かってプログラミングし、境界を明示する**。

**④ 設定より規約**：`@導出(ひとしい)` の 1 行が手書き数十行のボイラープレートに代わる——「機械が機械的に生成できるものを、人が手書きしない」。`@テスト`/`@期待` はテストの敷居をゼロにする。

## 練習

1. ジェネリック関数 `交換<T>(甲: T, 乙: T): (T, T)` を書き、交換したタプルを返そう。整数と文字列の両方で呼んでみよう；
2. ジェネリック関数 `さがす<T>(データ: はいれつ<T>, 目標: T) そのなか T <: ひとしい: せいすう` を書こう——見つかれば添字、なければ -1；
3. `@ひょうじ式` マクロを書こう：`ひょうじ("<式のテキスト> = " + <式の値>)` へ展開する（ヒント：`$(input.toString())` と `$(input)` をそれぞれ 1 回使う）；
4. `zhc expand` で自分のマクロの展開ビューを見て、位置マッピングを確かめよう；
5. `構造体 学生` に `ひとしい` を派生させ、フィールドが同じ 2 つのインスタンスで `==` が真になるのを確かめよう。

## まとめ

- ジェネリクス：`関数 名<T>(...)` / `型<T>`。呼び出しは自動推論。`そのなか T <: ひかくかのう` で能力を限定；
- マクロパッケージは先頭行 `macro package <名>`（公式文法 + `import std.ast.*`）。マクロのシグネチャは `(Tokens) -> Tokens`。呼び出しは `@マクロ名(...)`。マクロ名は日本語でもよい；
- 二段階コンパイル：`cjc マクロパッケージ --compile-macro` → `cjc メインプログラム`。`zhc run` はマクロパッケージ非対応——`zhc expand --macro-pkg` で検証する；
- `quote()` でコードを組み立て、`$(...)` は**コード位置でのみ**挿入する（`$(input)` はコードを埋め込み、`$(input.toString())` はテキストを挿入）。文字列挿入の `${...}` とは別物；
- `@導出(ひとしい)` がボイラープレート実装を自動生成。`@テスト`/`@期待` は内蔵テストフレームワーク（import は二つとも必須）。
