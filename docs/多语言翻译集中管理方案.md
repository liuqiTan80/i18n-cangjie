# 多语言翻译集中管理方案（设计 §19）

> 问题：同一个第三方库需要同步维护 zh/fr/ko/… 多种母语翻译版本，若把各语言
> 映射直接写进源码仓库，仓库会随语言数线性膨胀，且用户被迫下载看不懂的
> 其他语言版本。本文给出「集中存放、按语言拉取、基线驱动同步」的完整方案，
> 并标注哪些能力已由 zhc 现有机制（§6.3 语言包加载、§17 share、§18 翻译
> 资源共享、libs 众包平台）覆盖，哪些属于增量实施项。

## 一、总体架构

翻译资产与源码解耦为三层，**主仓库只保留 zh 基线与加载器，其他语言全部外置**：

```text
┌─ 主仓库（zwCangjie）──────────────┐
│  zhc/lang-packs/zh/   zh 基线词表（教学锁定区，保证离线最小可用） │
│  zhc/src/…            加载器/转译器/门禁（不含任何译文）        │
│  libs/index.json      共享仓库指针（默认 base 指向翻译资源中心）│
└──────────────┬───────────────────┘
               │ fetch --lang <母语>（按需，单文件/整包）
┌─ 翻译资源中心（独立平台）─────────┴───────────────────────────┐
│  独立 Git 仓库（translations）+ share_server.py 自托管端点      │
│  或任意静态托管；CI 门禁（check-libs 口径）+ 人工审校            │
│  crates/<语言>/<库名>.toml + index.json + groups/<库名>.json    │
└──────────────┬───────────────────────────────────────────────┘
               │ fetch（仅所选语言）
        用户 ~/.zhc/lang-packs/<母语>/ + crates/   ← ZHCLANG 运行时生效
```

设计原则（对应问题三点）：
1. **不进源码**：译文只存在于资源中心；主仓库语言数恒为 1（zh 基线），克隆体积与语言数无关；
2. **按需拉取**：任何一次下载的最小粒度是「单个库 × 单个语言」（`share fetch` 已实现），最大粒度是「单个语言整包」（新增 `lang pull`）；
3. **zh 为基线（pivot）**：所有语言版本翻译自 zh 基线，同步更新围绕「基线指纹」展开。

## 二、映射表的数据组织方式

**物理布局**（沿用 §18 已实现的注册表布局，zhc 加载器零改动）：

```text
<Hub>/index.json                      全局索引（§18 格式：名称/语言/描述/作者/键数/校验和/时间）
<Hub>/crates/<语言>/<库名>.toml       单语言映射（键 = 母语名，值 = 官方原名，格式同 libs/README.md 守则）
<Hub>/packs/<语言>.tar.gz             语言包整包（keywords/stdlib/module_paths/errors/ui，按 §语言包开发.md 结构）
<Hub>/groups/<库名>.json              【新增】同库多语言分组视图（同步维护的核心）
```

**TOML 文件内部结构不变**，仅头部增加两行溯源注释（供同步与审校，加载器忽略）：

```toml
# 基线: zh@7873ff850e9e2fc4        ← 翻译自哪一版 zh 基线（hash64 校验和）
# 组: csv4cj                        ← 所属库分组（各语言版本共享）
["标识符"]
"CSV解析器" = "CSVParser"
…
```

**分组视图 `groups/<库名>.json`**（新增，纯元数据，很小）——回答「这个库现在有哪些语言版本、谁落后了」：

```json
{
  "名称": "csv4cj",
  "基线": {"语言": "zh", "校验和": "7873ff850e9e2fc4", "键数": 73, "时间": "…"},
  "版本": [
    {"语言": "fr", "校验和": "…", "键数": 71, "基线": "7873ff850e9e2fc4", "状态": "落后"},
    {"语言": "ko", "校验和": "…", "键数": 73, "基线": "7873ff850e9e2fc4", "状态": "同步"}
  ]
}
```

`状态` 判定规则：条目的 `基线` 指纹 == 组 `基线.校验和` → `同步`；否则 `落后`
（基线升级后未跟进）；`键数` 差值即大概缺口。index.json 条目同步增加 `组`
字段，保证两种视图一致（server 写入时一并维护）。

**语言包整包**（keywords 等词表）与库映射分开管理：词表是「语言级」资产
（一种语言一份），库映射是「库 × 语言」资产（一库多份）；前者用整包 tarball
分发，后者用单文件按需分发——粒度不同，通道相同（同一个 base）。

## 三、存放位置与加载机制

**存放位置**：翻译资源中心 = 独立 Git 仓库（评审走 PR）+ 可选自托管端点
（`tools/share_server.py`，已实现，零依赖）。主仓库内的 `libs/` 降级为
「zh 基线 + 指针」：`libs/index.json` 只登记官方 Hub 地址，`DEFAULT_SHARE_BASE`
指向 Hub（可被 `ZHC_SHARE_BASE` / `~/.zhc/share.toml` 覆盖——三级解析已实现）。
迁移路径：现 `libs/zh/crates/*.toml` 是 zh 基线种子，保留；其他语言一律不进主仓。

**加载机制**（三层全部已具备，或仅需小改）：

| 层 | 内容 | 加载方式（现状） | 状态 |
|---|---|---|---|
| 内核词表 | zh 基线 keywords/… | 主仓库 `lang-packs/zh/` 静态内置 | 已有（锁定区） |
| 其他语言词表 | ko/fr/… 语言包 | `~/.zhc/lang-packs/<代码>/` 用户目录，`zhc lang install` 装入；resolveLangPack 用户目录优先级高于内置 | 已有 |
| 库映射 | crates/<语言>/<名>.toml | `share fetch --lang` 装入语言包 crates/，随语言包按 §6.3 后载覆盖语义合并 | 已有 |
| 回退 | UI 文案/诊断消息缺键 | 运行时优雅回退中文原文（语言包加载器内建） | 已有 |

即：**加载器不需要为多语言集中管理做任何改造**，集中化只改变「译文放在哪、
怎么取」，不改变「怎么用」。

## 四、拉取时指定语言的实现方案

分两个层次（运行时选择与拉取选择分离成两个变量）：
- `ZHCLANG`：运行时用哪种方言（已有）；
- `ZHC_PULL_LANG`【新增】：拉取时默认语言，缺省跟随 `ZHCLANG`。

**层次 1：库映射按语言拉取（已实现）**

```bash
zhc share fetch csv4cj --lang fr        # 只下载 csv4cj 的 fr 版单文件（缺 fr 版时报已有语言清单）
zhc share search csv4cj                 # index 按 语言/名称/描述 检索
```

**层次 2：批量与整包（增量实施项）**

```bash
# ① 按项目依赖批量拉取：读 cjpm.toml [dependencies]，逐库拉所选语言映射；
#    缺该语言版本 → 回退拉 zh 版并打印 [回退] 提示（程序仍可跑，译文后补）
zhc share fetch --deps --lang fr

# ② 语言包整包拉取：一种语言一份 tarball，装到 ~/.zhc/lang-packs/<代码>/
zhc lang pull ko                        # = share fetch packs/ko.tar.gz + lang install

# ③ 拉项目时指定语言（三选一，按场景）：
install.sh --lang ko                    # 离线发布包按语言拆附件，装包即带所选语言
bash scripts/clone-lang.sh ko           # git clone --filter=blob:none --sparse +
                                        # sparse-checkout set zhc/lang-packs/ko libs
zhc init 我的项目 && zhc lang pull ko   # 常规 clone（主仓无其他语言，本就小）+ 按语言补译文
```

臃肿问题的量化结论：主仓库语言数恒为 1；用户本地新增资产 = 所选语言的
语言包（几十 KB）+ 所用库的所选语言映射（每个几 KB）。任何用户都不会
接触其他语言的字节。

## 五、同步更新与维护流程

围绕**基线指纹**（`hash64` 校验和，§18 已实现同款算法）驱动：

```text
库 X 上游升级 / 新增 API
   │ ① zhc translate（或 mapping auto）重生成 zh 基线 → share publish（组 X）
   ▼
Hub 更新组 X 的「基线.校验和」→ 各语言条目自动变为「落后」（指纹不等）
   │ ② zhc share sync-report X            【新增】列出组内各语言状态与缺口
   ▼
翻译者按缺口补译：share fetch X --lang zh（取最新基线做参照）
   → 修订 fr.toml 头部「基线: zh@<新指纹>」→ share publish 覆盖
   │ ③ publish 双端门禁（格式/官方名/撞词表/校验和，Cangjie 端 + server 端同口径）
   ▼
审校 + 合并：Hub 独立仓库走 PR（review 各语言 diff）；自托管端点可直录，
   定期由维护者导出 Git 快照存档（发布即冻结，可回滚）
   │ ④ CI 门禁：check-libs 口径 + verify-lang-packs（跨语言覆盖集一致）
   ▼
用户侧：zhc share fetch X --lang fr 重新拉取 → 落后解除
```

配套约定：
- **术语一致性**：每种语言一份术语表（语言包头注，ko/fr 已示范）+ 撞词表门禁；
  同库各语言独立成文、互不覆盖，翻译者只面对自己语言；
- **恒等保留规则跨语言一致**：get/size/print 等通用短名所有语言都不译（全局别名安全）；
- **冲突处理**：同语言同库重复 publish = 更新（幂等，§18 已实现）；跨语言同名并存合法；
- **废弃语言**：groups 视图标记 `状态: 停维护`，index 保留条目，`fetch` 时提示。

## 六、增量实施项清单（本方案相对现状的新增工作）

| # | 项 | 说明 | 规模 |
|---|---|---|---|
| 1 | `groups/<库名>.json` + `share sync-report` | 分组视图与落后报告（share.cj 增一个子命令 + server 增一段写逻辑） | 小 |
| 2 | `share fetch --deps` | 按 cjpm.toml 依赖批量拉取（含 zh 回退提示） | 小 |
| 3 | `lang pull <代码>` | 语言包整包拉取（复用 fetch 通道 + lang install） | 小 |
| 4 | `scripts/clone-lang.sh` / `install.sh --lang` / `release.sh --lang` | 拉源码时指定语言的三个入口 | 小 |
| 5 | Hub 独立仓库迁移 | 新建 translations 仓库承接多语言内容，主仓 libs/ 只留 zh 基线与指针；`sync-libs.sh` 不变 | 中（流程性） |
| 6 | `ZHC_PULL_LANG` | 拉取默认语言变量（fetch/lang pull 读取） | 极小 |

## 七、方案对比与取舍

- **为什么不把多语言映射继续放主仓库**（现状 libs/zh + 未来 fr/ko 目录）：
  仓库体积随语言数与库数线性增长；PR 审校混杂；用户被迫全量下载——正是本方案
  要消除的三点。zh 基线留在主仓是例外且必要：它是教学锁定区、离线最小可用集
  （无网络也能 `zhc run hello.zc`）；
- **为什么按库分组而不是按语言分组管理同步**：同步的单位是「库升级事件」，
  分组视图直接回答「X 库升级后哪些语言要跟」，按语言组织则每次都要全量交叉比对；
- **为什么用校验和指纹而非版本号**：映射内容是平铺键值，无语义版本概念；
  hash64 指纹由内容唯一决定，publish 幂等、对比零成本，且算法已在 zhc/server
  双端实现（§18）。
