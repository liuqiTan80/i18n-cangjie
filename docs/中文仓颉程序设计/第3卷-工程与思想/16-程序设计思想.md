# 第 16 章 程序设计思想

> **本章学习目标**：把前面各章的「设计思想」汇总成体系——语法是表，思想是里。理解仓颉为什么这么设计之后，语法不再需要死记。
> **读完本章你能回答**：仓颉用哪三种机制消灭内存灾难？为什么 `让` 是默认？穷尽性检查保护你什么？

---

## 16.1 什么是程序设计思想

**定义**：程序设计思想 = 语言设计者在语法背后做的**价值取舍**。每个语法特性都在回答一个问题：「我们牺牲了什么，换来了什么？」

| 语言特性 | 牺牲 | 换来 |
|---|---|---|
| 无 `null`（选项） | 写起来多一层解包 | 空指针 bug 绝迹 |
| 默认不可变（`让`） | 多敲一个 `可变` | 意外修改/并发竞争大幅减少 |
| 显式 `开放`/`重写` | 多敲两个关键字 | 继承关系清晰可控 |
| 穷尽性检查 | 匹配必须写全分支 | 漏分支在编译期暴露 |

**为什么**：新手只学「怎么用」，老手追问「为什么这么设计」——后者才是举一反三的能力来源：理解了取舍，遇到新语言/新 API 时能自己推断设计意图，而不是死记。

## 16.2 内存安全：没有 null 的世界

**思想**：C/C++ 几十年被**空指针**与**悬垂引用**两类 bug 困扰（安全漏洞大头）。仓颉选择「编译器严格一点、程序员自由少一点」——把错误挡在编译期，而不是运行时崩溃。

**表现**：

- **没有 `null` 关键字**：可空性进入类型系统——`选项<T>` 要么 `有值(x)` 要么 `无值`（第 14 章）；
- **悬垂引用**：引用生命周期由编译器管理（所有权/借用检查），用过的内存不会「悬空」；
- **错误提示落地**：`不能给不可变值赋值`、`类型不匹配` 都是这条思想在诊断中的体现。

## 16.3 值类型与引用类型的分工

**思想**：类型分两类——**值类型**（拷贝语义：整数、结构体、枚举、元组）与**引用类型**（共享语义：类、数组、字符串、接口）。两种语义各有适用场景，**数据结构决定语义，而不是调用方**：

| | 值类型 | 引用类型 |
|---|---|---|
| 赋值 | 整体拷贝（无别名） | 共享引用（有别名） |
| 优点 | 可预测、线程安全、无意外串改 | 不复制大对象、多态必需 |
| 代表 | `结构体`、枚举、元组 | `类`、数组、字符串 |

**经验法则**：数据小且独立用结构体；需要多态/共享用类（第 12 章）。改拷贝不影响原值——「无别名」让推理简单：一个变量只被一处修改。

## 16.4 不可变默认（`让` 优先）

**思想**：可变性是 bug 的主要来源（意外修改、并发竞争、难以推理）。仓颉把「不可变」设为默认值——**可变变成需要申请的特权**。读代码时扫一眼 `可变` 就知道哪里可能变化：

```cangjie
主函数() {
    让 配置 = "固定值"       // 不可变：读代码时不需要担心它变
    可变 计数 = 0            // 可变：只有这里可能变化，重点盯防
}
```

**表现**：`让` 是默认、参数只读、结构体字段需 `修改` 才可改、字符串不可变（第 9/12 章）。

**并发红利**（第 14 章）：不可变数据**不需要同步**——不会被并发修改、不会数据竞争。并发程序里尽量 `让`，只有真正共享的可变状态才需要 `同步`/原子。

## 16.5 类型推断与强类型

**思想**：兼得两派优点——**动态语言的书写体验**（少写类型标注）+ **静态语言的安全性**（编译期全查）。设计原则：**可推断处不写，关键处必写**：

```cangjie
主函数() {
    让 x = 90                // 推断：整数
}
函数 加倍(数: 整数): 整数 { 返回 数 * 2 }   // 参数必须标注——接口契约显式化
```

**表现**：局部变量与返回类型可推断；**函数参数必须标注类型**（这是接口契约的一部分）；泛型调用自动实例化（第 15 章）。

## 16.6 多范式融合：表达式即值

**思想**：没有一种范式通吃所有问题。仓颉吸收而非排他——逻辑用命令式写、数据处理用函数式写、系统建模用 OO 写，各取所长：

```cangjie
主函数() {
    让 分数 = 85
    让 评级 = 如果 (分数 >= 60) { "及格" } 否则 { "不及格" }   // 如果 是表达式：有值
    打印行(评级)

    让 描述 = 匹配 (分数) {                                    // 匹配 是表达式：有值
        情况 x 其中 (x >= 90) => "优秀"
        情况 _ => "其他"
    }
    打印行(描述)
}
```

**表现**：`如果`/`匹配` 是表达式（函数式）也支持语句风格（命令式）；`匹配` 穷尽性检查 + `映射`/`过滤` 链式（函数式）+ 类层次（OO）并存。**「表达式即值」让代码更紧凑**：赋值与分支合而为一，少写临时变量。

## 16.7 模式匹配与穷尽性检查

**思想**：`如果` 链是「手动管理分支」——漏写一个 `否则` 编译器不吭声，运行时悄悄走错路。穷尽性检查把「分支完整性」变成**编译错误**——这是仓颉从函数式语言继承的最强安全设计之一（第 13 章）。

**表现**：匹配枚举/选项/元组必须穷尽（或 `_` 兜底）；`情况 有值(名字)` 同时判断+解构；新增枚举成员时，所有匹配点编译报错——**强迫你处理新情况**（可扩展性的安全网）。

## 16.8 显式优于隐式：接口契约可视化

**思想**：把「可能出错的地方」都变成**显式的编译期检查**，代价是多敲几个词，收益是少一类 bug。仓颉的显式设计清单：

| 显式标记 | 防止的错误 |
|---|---|
| `开放` 才可继承 | 意外继承破坏封装 |
| `重写` 才可覆盖 | 拼错方法名变成新方法 |
| `修改` 才可改结构体自身 | 副本悄悄变化 |
| `作为` 才可向下转换 | 类型错配 |
| `约束 T <: 可比较` | 泛型代码调用不存在的方法 |
| 参数类型必须标注 | 接口契约模糊 |

**思想内核**：**默认封闭、默认不可变、默认显式**——三个「默认」把特权变成申请制。读代码时，扫一眼显式标记就知道「哪里允许变化、哪里允许扩展」。

## 16.9 扩展：开放世界设计

**思想**：经典 OO 的「修改类」有两个痛点：无权改（标准库/第三方）、改了影响所有人（脆弱）。`扩展` 把「添加行为」变成**外挂式**操作——每个模块给自己关心的类型挂方法，互不干扰：

```cangjie
扩展 整数 {
    公开 函数 加倍(): 整数 { 返回 本对象 * 2 }
}

主函数() {
    打印行(21.加倍())        // 42（扩展方法像原生方法一样调用）
}
```

**表现**：字符串/集合的方言方法名（`修剪`/`分割` 等）大量依赖扩展机制实现；**组合优于继承**：能用组合表达的 has-a 关系不要硬造继承。

## 16.10 错误处理哲学

**思想**：错误处理是**设计决策**不是语法——每个失败场景先分类（第 14 章）：

- **预期失败**（输入、查无、越界）→ `选项`：失败是返回值的一部分，调用方必须处理；
- **意外错误**（bug、环境）→ 异常：沿调用栈自动上抛，谁有能力谁捕获；
- **Fail fast**：`获取或抛出()`、前置检查——错误越早暴露越容易修，把错误吞掉是最危险的代码；
- **不要用异常做控制流**：性能与可读性都差。

## 16.11 声明式数据处理

**思想**：把「遍历 + 条件判断 + 收集」压缩成一步——**声明式**代码说「做什么」（过滤掉不及格的），**命令式**代码说「怎么做」（建列表、循环、判断、添加）。意图直说，读者不必翻译：

```cangjie
导入 标准集合.*
主函数() {
    可变 成绩 = 向量<整数>()
    成绩.添加(95); 成绩.添加(45); 成绩.添加(70)
    让 及格 = 成绩 |> 过滤({ x => x >= 60 }) |> 收集数组   // 声明式
    打印行(及格.大小)       // 2
}
```

**配套思想**：**惰性求值**——`映射`/`过滤` 返回迭代器，被消费（`收集数组`）时才真正计算；**原容器不变**——函数式风格下原数据是「输入」，不会被悄悄改掉。

## 16.12 元编程：编译期求值

**思想**：把「每次运行都做的重复工作」提前到「编译时做一次」——宏在编译期运行，运行时只剩展开结果，**零开销**；宏崩溃 = 编译错误（好事），错误在最早时刻暴露（第 15 章）。

**三条安全设计**（对比 C 预处理器的文本替换）：

- **卫生宏**：不会意外捕获调用方变量；
- **类型化**：输入输出都是 `Tokens`；
- **无 IO**：宏不能读文件/访问网络——保证构建可复现。

**时机判断**：90% 的「重复代码」用函数/泛型就能消除；只有需要**操作代码本身**时才轮到宏——宏是最后手段，不是第一选择。

## 16.13 zhc 方言的设计思想

**① 术语母语化（中文即代码）**：方言不是「翻译文档」，而是把语言本身翻译成中文——关键字、标准库、错误消息全部中文。编程的认知负担分两层：**算法思维**（本来就是中文思维）与**语言门槛**（英文关键字）——方言移除第二层，「用中文思考，用中文表达」。

**② 诊断即教学**：编译器错误是学习的第一现场——初学者 70% 的时间在跟编译器对话。中文诊断把「错误信息」变成「教学材料」：告诉你怎么错了（💡）、怎么改（修复示例）——这是 zhc 相对官方编译器的**增值层**。

**③ 转译即查表**：方言不是新语言，而是「词表驱动的重写规则」——查表替换 + 上下文保护（字符串不误改、声明名豁免、插值保护）。理解这个设计，就理解了为什么改词表能造出新方言。

**④ 语言包可扩展（方言即配置）**：整个方言是一组**数据文件**（词表/消息表），不是写死的代码逻辑——**转译引擎与语言包解耦**：语言包可独立演进、可校验（`mapping check`）、可扩展（自定义错误码）。换一套词表就是一门新方言——这是「语言无关」的根基。

## 小结

- 程序设计思想 = 语法背后的价值取舍：牺牲一点便利，换取一类 bug 绝迹；
- 仓颉四大基石：内存安全（无 null）、不可变默认、显式契约、穷尽性检查；
- 多范式融合：命令式写逻辑、函数式写数据、OO 写系统，各取所长；
- 错误处理哲学：预期失败用选项、意外用异常、快速失败；
- zhc 四条思想：母语化、诊断即教学、转译即查表、语言包可扩展。
