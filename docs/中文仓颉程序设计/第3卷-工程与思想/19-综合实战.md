# 第 19 章 综合实战：完整项目

> **本章学习目标**：把全书知识串成一个**完整的真实项目**——需求 → 设计 → 测试先行 → 实现 → 调试 → 重构 → 提交 → 发布，走一遍软件工程全流程（第 18 章方法论的实战落地）。
> **读完本章你能回答**：一个「能用」的程序是怎么从一句话需求长成的？测试先行为什么让代码更干净？

## 19.1 项目选题：猜数字游戏

**需求（一句话）**：电脑心里想一个 1 到 100 的整数，你来猜，电脑告诉你「大了」「小了」「猜对了」，并统计你猜的次数。

**验收标准**：

- 每次游戏随机想一个 1..100 的数（每次运行都不同）；
- 输入非法（不是数字）提示并重新输入，**不崩溃**；
- 猜对后显示次数，并询问「再来一局？」；
- 输入「退出」随时结束。

**设计决策**（每一条都对应本书的一个知识点）：

| 需求点 | 设计 | 知识点 |
|---|---|---|
| 随机数 | 随机模块 | 导入与模块路径（第 10 章） |
| 输入可能非法 | `选项` 解析函数 | 预期失败用选项（第 14 章） |
| 循环猜直到猜对 | `当 (真)` + `跳出` | 循环控制（第 6 章） |
| 大小比较 | `如果/否则如果` | 分支（第 5 章） |
| 再来一局 | 外层循环 + 布尔状态 | 循环嵌套（第 6 章） |

## 19.2 测试先行：先写测试

**思想**：先写「这个函数应该怎么表现」的测试，再写实现——测试就是需求的可执行版本。核心逻辑拆成**纯函数**（无输入输出依赖、好测）：

```cangjie
导入 标准测试宏.*
导入 标准测试.*
导入 正则.*
导入 转换.*

// —— 被测函数（19.3 会正式实现，这里先定义好行为）——

函数 检查猜测(秘密: 整数, 猜测: 整数): 字符串 {
    如果 (猜测 < 秘密) { 返回 "小了" }
    否则如果 (猜测 > 秘密) { 返回 "大了" }
    返回 "对了"
}

函数 解析数字(文本: 字符串): 选项<整数> {
    如果 (正则("^\\d+$").匹配正则(文本)) {   // 锚定 ^...$：整串是数字才过（\d+ 是包含匹配）
        返回 有值(整数.解析(文本))
    }
    返回 无值
}

@测试
函数 测试检查猜测() {
    @期望(检查猜测(50, 30), "小了")     // 猜小了
    @期望(检查猜测(50, 70), "大了")     // 猜大了
    @期望(检查猜测(50, 50), "对了")     // 猜对了
    @期望(检查猜测(1, 1), "对了")       // 边界：最小值
    @期望(检查猜测(100, 100), "对了")   // 边界：最大值
}

@测试
函数 测试解析数字() {
    @期望(解析数字("42").获取或抛出(), 42)   // 合法输入
    @期望(解析数字("abc").获取或默认({ => 0 }), 0)   // 非法输入 → 兜底 0
    @期望(解析数字("").获取或默认({ => 0 }), 0)      // 空输入 → 兜底 0
    @期望(解析数字("a1").获取或默认({ => 0 }), 0)    // 边界：含数字但不全数字（不锁会被漏过！）
    @期望(解析数字("1a").获取或默认({ => 0 }), 0)    // 边界：后含字母
}
```

**注意**：测试先行时函数**先写声明**（甚至先写假实现），跑测试看到失败（红），再实现让它通过（绿）——这叫「红-绿-重构」节奏。上面代码直接给了完整实现，实际操作时先删掉函数体跑一次失败的。

## 19.3 实现：完整游戏

**项目结构**（用 `zhc init` 创建）：

```
猜数字/
├── cjpm.toml
└── src/
    └── main.zc
```

**完整代码**（`src/main.zc`）：

```cangjie
导入 环境.*
导入 转换.*
导入 正则.*
导入 随机.*
导入 标准测试宏.*
导入 标准测试.*

// —— 核心逻辑：纯函数（可测试）——

函数 检查猜测(秘密: 整数, 猜测: 整数): 字符串 {
    如果 (猜测 < 秘密) { 返回 "小了" }
    否则如果 (猜测 > 秘密) { 返回 "大了" }
    返回 "对了"
}

函数 解析数字(文本: 字符串): 选项<整数> {
    如果 (正则("^\\d+$").匹配正则(文本)) {   // 锚定：整串必须全是数字
        返回 有值(整数.解析(文本))
    }
    返回 无值
}

// —— 交互逻辑：单局游戏 ——

函数 玩一局() {
    让 生成器 = Random()                    // 随机数生成器（官方类名，方言暂未收录）
    让 秘密 = 生成器.下一个整数(100) + 1   // 1..100（nextInt64(100) 得 0..99）
    可变 次数 = 0
    打印行("我心里想了一个 1 到 100 的整数，来猜！")
    当 (真) {
        次数 += 1
        打印行("第${次数}次猜：")
        让 输入 = 读取行()
        如果 (输入 == "退出") { 返回 }          // 随时退出
        让 数字 = 解析数字(输入).获取或默认({ => -1 })   // 无效输入兜底 -1
        如果 (数字 == -1) {
            打印行("请输入数字哦（或输入「退出」）")
            次数 -= 1                       // 无效输入不算次数
        } 否则 {
            让 结果 = 检查猜测(秘密, 数字)
            如果 (结果 == "对了") {
                打印行("🎉 猜对了！答案是 ${秘密}，你用了 ${次数} 次。")
                返回
            } 否则 {
                打印行("${结果}，再试！")
            }
        }
    }
}

// —— 入口 ——

主函数() {
    打印行("== 猜数字游戏 ==")
    当 (真) {
        玩一局()
        打印行("再来一局？（输入 退出 结束，其他任意键继续）")
        如果 (读取行() == "退出") { 跳出 }
    }
    打印行("再见！")
}
```

> 💡 为什么这里不用 `匹配`？官方 1.0.5 实测：`匹配` 分支体必须是**表达式**（`情况 X => 表达式`），多语句分支要写成块会报「期望 `=>`」。所以多语句分支改用 `获取或默认` 兜底 + `如果/否则`——效果一样，还更直白（第 13 章的 `匹配` 表达式体写法在 19.7 挑战 5 有练）。

**运行**：

```bash
zhc run src/main.zc
```

**实测对局**：

```
== 猜数字游戏 ==
我心里想了一个 1 到 100 的整数，来猜！
第1次猜：
50
小了，再试！
第2次猜：
75
大了，再试！
第3次猜：
62
🎉 猜对了！答案是 62，你用了 3 次。
再来一局？（输入 退出 结束，其他任意键继续）
退出
再见！
```

**逐块拆解**（本项目用到的一切）：

| 代码 | 作用 | 知识点 |
|---|---|---|
| `生成器.下一个整数(100) + 1` | 生成 1..100 的随机数 | 模块导入（第 10 章）；`Random`/`nextInt64` 为官方库名（zh 词表暂未收录，可直接使用） |
| `解析数字` 返回 `选项` | 非法输入不崩溃 | 预期失败用选项（第 14 章） |
| `解析数字(输入).获取或默认({ => -1 })` | 无效输入兜底 -1，不崩溃 | 选项兜底（第 14 章） |
| `当 (真)` + `跳出`/`返回` | 无限循环直到满足条件 | 循环控制（第 6 章） |
| `次数 -= 1` | 无效输入不算次数 | 复合赋值（第 9 章） |
| `检查猜测` 纯函数 | 核心逻辑独立可测 | 函数设计（第 7/8 章） |

## 19.4 测试与调试

**跑测试**：

```bash
zhc test
```

```
[ 通过 ] 用例： 测试检查猜测
[ 通过 ] 用例： 测试解析数字
汇总：共 2
    通过： 2, 跳过： 0, 错误： 0
    失败： 0
```

**故意制造一个 bug 练习调试**：把 `检查猜测` 里的 `猜测 < 秘密` 改成 `猜测 <= 秘密`——运行测试，`@期望(检查猜测(50, 50), "对了")` 会**红**（变成「小了」）。这就是回归测试的价值：改坏的东西立刻现形。

**调试流程**（五步法，第 18 章）：

1. 分类：这是逻辑错误（编译通过、行为不对）；
2. 最小复现：`检查猜测(50, 50)` 一行就够；
3. 读输出：`@期望` 失败会显示实际值（"小了"）vs 期望值（"对了"）；
4. 二分定位：`<=` 还是 `<` 的问题——比较边界；
5. 修复验证：改回 `<`，`zhc test` 全绿。

## 19.5 重构：让代码更干净

**定义**：重构 = 不改行为、只改结构（测试保证没改坏）。这个项目可以做的重构：

**① 提取常量**（魔法数字 1、100 是坏味道）：

```cangjie
导入 随机.*
常量 最小数 = 1
常量 最大数 = 100

函数 玩一局() {
    让 生成器 = Random()
    让 秘密 = 生成器.下一个整数(最大数) + 最小数
    // ...其余不变（与 19.3 完整代码组合使用）
}
```

**② 提取「是否再来一局」为函数**（主函数只留流程）：

```cangjie
函数 想再来一局(): 布尔 {
    打印行("再来一局？（输入 退出 结束，其他任意键继续）")
    返回 读取行() != "退出"
}

主函数() {
    打印行("== 猜数字游戏 ==")
    当 (真) {
        玩一局()          // 与 19.3 完整代码组合使用（片段）
        如果 (非 想再来一局()) { 跳出 }
    }
    打印行("再见！")
}
```

**③ 无效输入提示提取为常量**（文案集中管理）。

> 重构的铁律：**每次重构跑一遍测试**。测试全绿 = 行为没变 = 重构成功。

## 19.7 拓展挑战

1. **难度分级**：猜数字改成「1 到 1000」，看看最多需要几次（提示：二分，2¹⁰=1024）；
2. **统计战绩**：用 `向量` 记录每一局的次数，游戏结束后打印「平均 X 次猜中」；
3. **电脑猜你的数字**：角色互换——你想一个数，电脑用二分法猜（提示：`当 (真)` + `读取行` 回答大了/小了/对了，第 17 章二分思想实战）；
4. **限制次数**：10 次没猜中判负（提示：`次数 >= 10` 时 `跳出` 并揭晓答案）；
5. **终极挑战**：把「检查猜测」的返回值从 `字符串` 改成 `枚举 结果 { 小了 | 大了 | 对了 }`，重构全项目——感受枚举 + 穷尽性检查如何让代码更安全（第 13 章）。

## 小结

- 完整项目流程：需求（一句话 + 验收标准）→ 设计（每个需求点对应一个知识点）→ 测试先行（红-绿-重构）→ 实现 → 调试（五步法）→ 重构（测试保底）→ 提交发布；
- 猜数字游戏用到：随机数、`选项` 解析与兜底、`当 (真)` + `跳出`、纯函数、嵌套循环——**全书知识的第一次总动员**；
- 测试先行让设计更干净：核心逻辑写成纯函数，交互与逻辑分离；
- 重构的铁律：不改行为，只改结构，每次跑测试；
- 发布清单：测试全绿 → 手动验证验收 → 文档 → lint → 打 tag。

## 思考题

1. 为什么「解析数字」返回 `选项` 而不是直接 `整数.解析` 后捕获异常？（提示：预期 vs 意外，第 14 章）
2. 主函数的 `当 (真)` 循环里嵌套 `玩一局` 的 `当 (真)`——这种嵌套循环的出口分别是什么？
3. 如果把 `检查猜测` 从纯函数改成「内部直接打印结果」，测试会变难还是简单？为什么？（提示：测试需要捕获输出）
4. 重构时为什么必须有测试保底？没有测试的重构会怎样？（提示：改坏了没人知道）
5. 终极挑战的枚举版本：`匹配 (结果)` 漏写一个分支会发生什么？（提示：穷尽性检查，第 13 章）
