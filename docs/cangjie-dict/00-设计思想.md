# 00 设计思想

> 字典的「为什么」卷：每个词条解答「仓颉为什么这么设计」「方言为什么这么翻译」。
> 学习语言，语法是表，思想是里——理解设计动机后，语法不再需要死记。

## 一、仓颉语言的设计思想

## 词条 0.1 内存安全（无空指针、无悬垂引用）

- **是什么**：仓颉从语言层面杜绝两类内存灾难：**空指针**（用 `选项<T>` 消灭 `null`）与**悬垂引用**（编译期所有权/借用检查）。
- **为什么**：C/C++ 几十年被这两类 bug 困扰（安全漏洞大头）。仓颉选择「编译器严格一点、程序员自由少一点」——把错误挡在编译期，而不是运行时崩溃。
- **表现**：没有 `null` 关键字；`选项` 必须显式处理；不可变默认（见 0.6）；引用生命周期由编译器管理。
- **方言侧**：`有值`/`无值`/`选项` 的中文词条都在语言包里（见 8.1-8.3）；错误提示「不能给不可变值赋值」「类型不匹配」都是这条思想的落地。

## 词条 0.2 值类型与引用类型（struct 与 class 的分工）

- **是什么**：类型分两类：**值类型**（拷贝语义：整数、结构体、枚举、元组）与**引用类型**（共享语义：类、数组、字符串、接口）。
- **为什么**：两种语义各有适用场景：值类型**无别名**（改拷贝不影响原值——线程安全、可预测）；引用类型**共享**（大对象不复制、多态必需）。仓颉把选择权交给类型作者——数据结构决定语义，而不是调用方。
- **表现**：`结构体` 默认值语义、`类` 默认引用语义；参数传递按类型自动选择（见 3.8）。
- **方言侧**：`结构体`/`类` 分两个词条（6.1/6.13），重点讲清这个差异。

## 词条 0.3 多范式融合（命令式 + 函数式 + 面向对象）

- **是什么**：一门语言同时支持三种范式：命令式（`如果`/`当`/循环）、函数式（lambda/匹配/不可变/高阶函数）、面向对象（类/接口/继承）。
- **为什么**：没有一种范式通吃所有问题。仓颉的设计哲学是**吸收而非排他**：逻辑用命令式写、数据处理用函数式写、系统建模用 OO 写——各取所长，而不是强迫开发者皈依某一派。
- **表现**：`匹配` 穷尽性检查 + `映射`/`过滤` 链式 + 类层次并存；`如果`/`匹配` 是表达式（函数式）也支持语句风格（命令式）。
- **方言侧**：字典按范式分卷（04 控制流/05 函数/06 面向对象），同一概念从不同范式视角交叉引用。

## 词条 0.4 宏与元编程（编译期代码生成）

- **是什么**：宏在**编译期**接收代码、生成代码（见 09 卷）。
- **为什么**：这是仓颉对标 C++ 模板/Rust 宏的「元能力」设计——很多语言靠「框架反射」在运行时模拟（慢、不安全），仓颉选择**编译期完成**（快、类型安全）。宏是「语言的可编程部分」：库作者可以用宏给语言加「语法糖」，而不必修改编译器。
- **表现**：`宏` 包 + `引用` + `@调用`；`@派生` 自动生成样板代码；`@测试`/`@期望` 本身就是宏（测试诊断能看到表达式文本）。
- **方言侧**：`宏`/`引用`/`派生`/`测试`/`期望` 全在语言包；`zhc expand` 教学视图展示宏展开（见 9.3）。

## 词条 0.5 类型推断（全量推断 + 强类型）

- **是什么**：局部变量与函数返回类型可由编译器推断，同时类型系统完全静态（见 2.13）。
- **为什么**：兼得两派优点——**动态语言的书写体验**（少写类型标注）+ **静态语言的安全性**（编译期全查）。设计原则：**可推断处不写，关键处必写**（函数参数必须标注——接口契约显式化）。
- **表现**：`让 x = 90` 自动推断 `整数`；`函数 名() { 返回 表达式 }` 返回类型可省；泛型调用自动实例化。
- **方言侧**：zhc 转译对类型标注原样保留（`分数: 整数` 照转），教学诊断在「类型不匹配」时给出修复示例。

## 词条 0.6 不可变默认（let 优先）

- **是什么**：变量默认不可变（`让`），可变需显式声明（`可变`）。
- **为什么**：可变性是 bug 的主要来源（意外修改、并发竞争、难以推理）。仓颉把「不可变」设为默认值——**可变变成需要申请的特权**。读代码时扫一眼 `可变` 就知道哪里可能变化。
- **表现**：`让` 是默认；参数只读；结构体字段需 `修改`（mut）才可改；字符串不可变。
- **方言侧**：`让`/`可变`/`修改` 是 03 卷核心词条；错误「不能给不可变值赋值」直接引导用 `可变`。

## 词条 0.7 模式匹配与穷尽性检查

- **是什么**：`匹配` + `情况` 的模式匹配，编译器强制覆盖所有分支（见 4.14-4.16）。
- **为什么**：`如果` 链是「手动管理分支」——漏写一个 `否则` 编译器不吭声，运行时悄悄走错路。穷尽性检查把「分支完整性」变成**编译错误**：编译器替你检查「所有情况都处理了吗」。这是仓颉从函数式语言继承的最强安全设计之一。
- **表现**：匹配枚举/选项/元组必须穷尽（或 `_` 兜底）；`情况 有值(名字)` 同时判断+解构。
- **方言侧**：`匹配`/`情况` 关键字中文化；教学诊断覆盖「非穷尽匹配」场景。

## 词条 0.8 扩展（extend）——开放世界设计

- **是什么**：不修改原类型即可添加方法（见 5.11）。
- **为什么**：经典 OO 的「修改类」有两个痛点：无权改（标准库/第三方）、改了影响所有人（脆弱）。扩展把「添加行为」变成**外挂式**操作——每个模块给自己关心的类型挂方法，互不干扰。
- **表现**：`扩展 字符串 { 函数 ... }`；扩展方法像原生方法一样调用。
- **方言侧**：`扩展` 关键字中文化；字符串/集合的方言方法名（`修剪`/`分割` 等）大量依赖扩展机制实现。

## 二、zhc 方言的设计思想

## 词条 0.9 术语母语化（中文即代码）

- **是什么**：方言不是「翻译文档」，而是**把语言本身翻译成中文**：关键字（`函数`/`让`/`如果`）、标准库（`打印行`/`向量`/`哈希映射`）、错误消息全部中文。
- **为什么**：编程的认知负担分两层：**算法思维**（本来就是中文思维）与**语言门槛**（英文关键字）。方言移除第二层——「用中文思考，用中文表达」，让初学者把全部注意力放在逻辑上。
- **表现**：58 个关键字词条 + 171 个标准库别名 + 645 条诊断码（见 10.12）。
- **注意**：母语化不是「翻译错」——每个词条都标注官方对应（本字典全程双写），随时可以对照官方文档。

## 词条 0.10 错误提示中文（诊断即教学）

- **是什么**：编译器错误不是冷冰冰的英文，而是**中文 + 💡 教学提示 + 修复示例**三段式（见 09 章教程与 12 卷入门书）。
- **为什么**：报错是学习的第一现场——初学者 70% 的时间在跟编译器对话。中文诊断把「错误信息」变成「教学材料」：告诉你怎么错了、为什么错、怎么改。
- **表现**：
  ```
  [错误] 类型不匹配  main.zc:3:14
    ↳ 期望 `整数`，实际得到 `结构体-字符串`
    💡 检查声明与赋值两侧类型是否一致……
    修复示例（可直接粘贴）：…
  ```
- **注意**：未知消息走「原文回退 + 记录」闭环（`zhc mapping check --missing` 可查未覆盖消息）。

## 词条 0.11 教学诊断（zhc 的三层诊断体系）

- **是什么**：zhc 的诊断输出分三层：**错误定位**（文件:行:列）、**教学提示**（💡 为什么错）、**修复示例**（可直接粘贴的正确代码）。
- **为什么**：传统编译器只给「定位 + 一句话」——初学者看了还是不会改。教学诊断补上「为什么」与「怎么做」两层，把错误从「障碍」变成「学习机会」。
- **表现**：全部错误码对应教学提示与修复示例（errors.toml 双表结构，见 09 章教程）；detail 行/note 行全中文。
- **注意**：这是 zhc 相对官方编译器的**增值层**——官方编译器没有教学提示；zhc 通过「消息表精确/模糊匹配」实现（见项目设计文档 §13.1）。

## 词条 0.12 语言包可扩展（方言即配置）

- **是什么**：整个方言是一组**数据文件**（词表/消息表），不是写死的代码逻辑——换一套词表就是一门新方言（见 10.12）。
- **为什么**：这是 zhc 的架构核心：**转译引擎与语言包解耦**。好处：语言包可独立演进（加词条/修翻译不改代码）、可校验（mapping check）、可扩展（自定义错误码如 `package_search_error`）。
- **表现**：`zhc/lang-packs/zh/` 五个 TOML 文件即方言本体；`ZHC_LANG_PACKS` 可指向其他语言包；`zhc mapping check --missing` 检测缺口。
- **注意**：语言包是**双向映射**（方言→官方用于转译，官方→方言用于错误提示与 expand 反向视图）——「忘记英语」与「可对照官方」兼得。
