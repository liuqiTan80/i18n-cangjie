# 11 软件工程知识

> 本章目标：从「写代码」升级到「造软件」——需求、结构、测试、调试、版本、规范六件套。全部知识用 zhc 工具链落地：学完就能用在本项目的开发中。
> 读完本章你能回答：单元测试为什么重要？调试的第一原则是什么？语义化版本怎么读？

## 11.1 软件工程是什么

**是什么**：写代码是「把想法变成程序」，软件工程是「**让程序可维护、可验证、可协作**」的整套纪律：

| 个人代码 | 工程项目 |
|---|---|
| 能跑就行 | 别人能看懂、能改 |
| 我自己记得改了什么 | git 记录每一次变更 |
| 跑一遍看结果 | 自动化测试守护每个功能 |
| 环境在我机器上 | 文档化 + 可复现构建 |

**为什么**：真实软件 90% 的时间在**修改**而不是从零编写——读代码的时间是写代码的 5-10 倍。工程纪律服务的对象是「未来的读者」（包括六个月后的你自己）。

## 11.2 需求分析：先想清楚做什么

**思想**：写代码前先回答三个问题——**给谁用**（用户）、**解决什么**（问题）、**怎么算成功**（验收标准）：

1. **一句话需求**：用一句话说清功能（「一个把摄氏温度转华氏度并打印的命令行工具」）；
2. **验收标准**：写清「怎样算做完」（输入 25℃ 输出 77℉；负数也支持）；
3. **最小可行**：先做最核心的一条路径，再迭代（先转温度，再加批量、再加交互）。

**实践**：用 `选项` 处理「输入可能非法」是需求分析的直接产物——需求说「输入可能是任意文本」，设计就写一个**返回 `选项` 的解析函数**（第 6 章）。**需求决定错误处理策略**。

## 11.3 项目结构与可复现构建

**是什么**：项目 = 声明配置（`cjpm.toml`）+ 约定目录（`src/`）+ 文档化的环境（第 1 章）：

```toml
[package]
name = "我的程序"
version = "0.1.0"
edition = "1.0.5"

[dependencies]
libdemo = { path = "../libdemo" }
```

**三条纪律**：

- **依赖声明化**：所有外部依赖写进 `[dependencies]`——别人 clone 项目后 `cjpm fetch` 一条命令装齐（第 8 章）；
- **环境文档化**：SDK 版本、环境变量（`CANGJIE_HOME`/`LD_LIBRARY_PATH`）、构建命令写进 README——换台机器也能重现（第 1 章）；
- **自动化脚本**：重复动作脚本化——本项目的 `scripts/release.sh`（打离线包）与 `acceptance.sh`（52 项验收）就是「把流程变成命令」的范例。

## 11.4 单元测试：给代码上保险

**是什么**：写一小段代码验证另一段代码的行为——没有测试的程序像没有刹车系统的车。仓颉标准库自带测试框架，zhc 全中文封装：

```cangjie
导入 标准测试宏.*
导入 标准测试.*

函数 评级(分数: 整数): 字符串 {
    如果 (分数 >= 60) { 返回 "及格" }
    返回 "不及格"
}

@测试
函数 测试评级() {
    @期望(评级(85), "及格")        // 期望表达式的结果为 85 分评级
    @期望(评级(40), "不及格")      // 边界与常规各测一个
}
```

项目根运行：

```bash
zhc test
```

```
[ 通过 ] 用例： 测试评级
汇总：共 1
    通过： 1, 跳过： 0, 错误： 0
    失败： 0
```

（「共 N」按 `@测试` 函数数统计，1.0.5 实测；本例 2 条 `@期望` 都属于这 1 个用例）

**测试三原则**：

| 原则 | 含义 | 反例 |
|---|---|---|
| **确定性** | 同一输入永远同一结果 | 测试依赖当前时间/随机数 |
| **独立性** | 每个测试互不依赖、可单独跑 | 测试 B 依赖测试 A 先执行 |
| **可读性** | 失败信息说清「哪个假设被打破」 | `断言(结果 == 5)` 不给上下文 |

**为什么值得写**：

- **回归保护**：改代码后跑一遍，立刻知道有没有改坏东西——重构的底气；
- **测试即文档**：测试展示了「这个函数应该怎么用、结果是什么」——比注释可信（注释会过期，测试过期会红）；
- **测试驱动设计**：写测试时被迫想清楚「输入/输出契约」——顺带把函数设计得更干净。

**断言选择**：`@期望(表达式, 值)`（宏，诊断带表达式文本）> `断言相等(实际, 期望)`（函数）> `断言(条件, "信息")`（布尔）；测试函数名以 `测试` 开头是惯例；每个测试独立、不依赖顺序。

## 11.5 调试方法论：错误是线索不是敌人

**思想**：调试 = 缩小「可能的出错范围」直到锁定。zhc 给你三件武器：**教学诊断**（第 9 章）、**lint 静态分析**（第 8 章）、**expand 转译视图**（第 7/8 章）。

**五步调试法**：

1. **先分类**：编译错误（诊断码前缀 lex/parse/name/sema/pkg 告诉你在哪个阶段，第 9 章）还是运行错误（异常/逻辑错）？
2. **复现最小化**：把出错的代码缩到最小——最小复现往往暴露真凶（删掉无关部分）；
3. **读错误全文**：zhc 诊断带 文件:行:列 + 💡 + 修复示例——**先照提示改，再理解为什么**；
4. **二分定位**：数据流中间插 `打印行` 看哪一步开始不对（打印调试）；或注释掉一半代码看错误消失在哪半；
5. **验证修复**：改完跑测试 + 故意再犯一次确认理解（第 9 章）。

**常见病根**（对照第 10 章思想自查）：

| 症状 | 病根 | 自查 |
|---|---|---|
| 值被「悄悄」改了 | 可变性失控 | 是不是该用 `让`/`结构体`（拷贝语义）？ |
| 空值崩溃 | 解包太急 | 该用 `匹配`/`获取或默认` 而不是 `获取或抛出`？ |
| 并发结果不定 | 共享可变状态 | 加 `同步` 或改不可变设计（第 6 章）？ |
| 行为依赖顺序 | 哈希容器遍历 | 不要依赖哈希映射/集合的顺序（第 4 章）？ |

## 11.6 版本控制与发布

**版本控制（git）**：工程协作的基石——记录每一次变更、支持回滚与协作：

```bash
git init                # 初始化仓库
git add 文件            # 暂存
git commit -m "信息"    # 提交（信息写清「改了什么、为什么」）
git log                 # 查看历史
```

**提交信息规范**：一行标题（动词开头：`新增`/`修复`/`重构`/`文档`）+ 必要时正文说明为什么。

**语义化版本**（SemVer）：`主版本.次版本.修订号`——读版本号就知道兼容性：

| 版本 | 含义 |
|---|---|
| `0.1.0` | 0.x：未稳定，随便改 |
| `1.0.0` | 第一个稳定版 |
| `1.2.0` | 次版本+1：新增功能（向后兼容） |
| `1.2.3` | 修订+1：修 bug（完全兼容） |
| `2.0.0` | 主版本+1：**破坏性变更**（用了 `1.x` 的代码要改） |

**发布流程**（以本项目为例）：全量实测（每个教程代码块跑通）→ 52 项验收脚本 → 打发布包（`scripts/release.sh`：编译 + 语言包 + 启动脚本）→ 写更新说明 → 打 tag。**发布前必跑测试，发布后必有记录**。

## 11.7 代码规范与可读性

**是什么**：代码是写给机器执行的，更是写给人读的。风格统一让团队协作不吵架：

```bash
zhc lint src/main.zc          # 风格检查（全角标点/尾随空白/行长度…）
zhc lint --fix src/main.zc    # 自动修复
```

**可读性五则**（方言版）：

1. **命名说意图**：`可变 总分` 好过 `可变 s`——中文命名让意图更直接；
2. **函数小而专**：一个函数只做一件事（超过 20 行考虑拆分）；
3. **注释说为什么**：代码说「怎么做」，注释说「为什么这么做」（这个奇怪的判断为什么存在）；
4. **DRY**：Don't Repeat Yourself——重复代码提取成函数/泛型/宏（第 7 章）；但**两次重复别急着抽象**（三次以上再说）；
5. **声明式优先**：`过滤`/`映射` 管道可读性优于手写循环（第 4 章）。

**代码审查**：给别人看你的代码（或看别人的）——审查不是找茬，是**四人眼原则**：写代码的人有盲区，第二双眼睛是质量关卡。审查重点：逻辑正确性、边界情况、命名、测试覆盖。

## 11.8 从需求到交付：完整案例

把本章六件套串成一个完整流程——「温度转换命令行工具」：

**① 需求**（11.2）：一句话 + 验收标准 + 最小可行：

```
需求：命令行输入摄氏度，输出华氏度
验收：输入 25 → 输出 77.0；输入 abc → 提示「不是数字」并不崩溃
```

**② 设计**：`选项` 处理解析失败（预期失败，第 6 章）；`主函数` 读输入、解析、计算、打印：

```cangjie
导入 环境.*
导入 转换.*
导入 正则.*

函数 转华氏(摄氏: 浮点): 浮点 {
    返回 摄氏 * 9.0 / 5.0 + 32.0
}

函数 解析摄氏(文本: 字符串): 选项<浮点> {
    如果 (正则("\\d+(\\.\\d+)?").匹配正则(文本)) {   // 先判断：是数字吗？
        返回 有值(浮点.解析(文本))                    // 是 → 成功
    }
    返回 无值                                        // 否 → 失败（预期失败用选项）
}

主函数() {
    让 输入 = 读取行()
    匹配 (解析摄氏(输入)) {
        情况 有值(摄氏) => 打印行("${转华氏(摄氏)}")
        情况 无值 => 打印行("不是数字")
    }
}
```

**③ 测试**（11.4）：先写测试再写实现（或并行）：

```cangjie
@测试
函数 测试转华氏() {
    @期望(转华氏(25), 77.0)
    @期望(转华氏(-40), -40.0)     // 边界：摄氏零下四十等于华氏零下四十
}
```

**④ 跑测试 + 手动验证**（11.5）：`zhc test` 全绿；手动输入 `abc` 验证优雅处理。

**⑤ 提交**（11.6）：`git add . && git commit -m "新增：温度转换工具"`；打 `0.1.0` 标签。

**⑥ 复盘**（可选）：有没有边界没测（`0` 度、最大值）？函数要不要拆？——**小步前进，每步可验证**。

## ✳ 设计思想

**① 工程纪律服务「未来的读者」**：可维护性 > 炫技。写代码时假设六个月后的自己会来改它——他会感谢你清晰的命名、诚实的注释、完整的测试。

**② 测试是投资不是成本**：每个测试的「成本」是写它的几分钟，「回报」是未来每一次修改的安心。测试覆盖率不是目标，**守护关键行为**才是（核心逻辑必测，样板代码可从简）。

**③ 小步前进，每步可验证**：需求切小（最小可行）、代码改小（小函数）、提交切小（小提交）——任何一步出错都能快速定位。这是对抗复杂性的唯一可靠策略。

**④ 工具链即纪律**：`zhc lint --fix` 让风格检查零成本、`zhc test` 让回归测试一键跑、git 让每一步可回滚——**好工具让好习惯变容易**（这就是 zhc 把工程命令全部中文化的意义：让纪律没有语言门槛）。

## 练习

1. 给自己 11.8 的温度工具补一个功能（如「支持多次输入直到输入 退出」），走完需求 → 测试 → 实现 → 提交全流程；
2. 用 `zhc lint` 检查你的项目，修复全部风格问题并提交；
3. 给 `评级` 函数（11.4）补边界测试：`60`（及格线）、`59`、`100`、`0`；
4. 找一个你已经写过的函数，用「五步调试法」为它制造一个 bug 再定位修复；
5. 阅读本项目 `acceptance.sh`，说出它守护了哪些「关键行为」——如果你是作者，会再加哪一项验收？

## 小结

- 软件工程 = 让程序可维护、可验证、可协作的纪律；需求先于代码，验收标准先于实现；
- 项目三件套：声明配置（cjpm.toml）+ 约定目录（src/）+ 文档化环境；
- 单元测试：`@测试` + `@期望`，`zhc test` 一键运行；确定性/独立性/可读性三原则；
- 调试五步：分类 → 最小复现 → 读全文 → 二分定位 → 验证修复；
- git + 语义化版本 + 发布流程让变更可追溯；`zhc lint` 让风格规范零成本。
