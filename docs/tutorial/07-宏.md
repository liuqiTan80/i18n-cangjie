# 07 宏

> 本章目标：理解「写代码的代码」——宏在**编译期**接收代码、产出代码；掌握宏包结构、`quote`（引用）插值与两步编译；会用 `@测试`/`@期望` 系统宏写单元测试。
> 读完本章你能回答：宏和函数有什么本质区别？`$(...)` 和 `${...}` 有什么不同？为什么要两步编译？

> ⚠️ 本章示例需要**宏包**目录结构，建议先 `zhc init` 建项目再操作（见第 8 章）。

## 7.1 宏是什么：编译期执行的代码变换器

**是什么**：宏是 `public macro 名字(input: Tokens): Tokens`（宏包内写**官方语法**，见 7.2）——吃代码 token，吐代码 token。调用写作 `@宏名(参数)`：

```cangjie
导入 调试.*

主函数() {
    让 x = 3
    @调试日志(x + 1)     // 示意：宏在编译期展开，普通运行环境无法演示
}
```

**为什么**：普通函数只能操作**值**（运行时）；宏能操作**代码本身**（编译期）。这带来三类函数做不到的事：

1. **语法糖再造**：把重复模式（记录日志、测量耗时）打包成宏调用；
2. **编译期检查**：在编译期验证模式（如 DSL 语法校验）；
3. **性能**：展开在编译期完成，**运行时零开销**。

**注意**：仓颉的宏是**卫生宏**（不会意外捕获调用方变量）+ **类型化**（输入输出都是 Tokens）——比 C 预处理器的文本替换安全得多；宏调用以 `@` 开头；宏名可用**中文**（官方支持中文标识符，如 `@调试日志`——zhc 转译时未命中的宏名**原样保留**）；宏展开错误在编译期报告（zhc 会把宏相关错误也转成中文提示）。

## 7.2 宏包与宏定义

宏必须定义在**宏包**中——源码**首行** `macro package 包名`。宏包只暴露宏（不能导出版本外的类型/函数）：

```cangjie
// define/define.cj —— 宏包源码（宏包内写官方仓颉语法，不经方言转译）
macro package define
import std.ast.*

public macro 调试日志(input: Tokens): Tokens {
    let 名字 = input.toString()
    return quote(
        println($(名字))
    )
}
```

要点（仓颉 1.0 宏规则，1.0.5 实测）：

- 首行 `macro package <包名>`（**官方语法**——宏包 `.cj` 文件不经方言转译，写 `宏 包`/`引用` 会编译报错）；
- 必须 `import std.ast.*`——`Tokens` 类型来自 `std.ast` 包（`std.macro` 不存在）；
- `public macro 名字(input: Tokens): Tokens`——参数与返回都必须是 `Tokens`；宏名可用**中文**（官方支持中文标识符）；
- 宏包是**独立编译单元**：先被编译成宏库（`.cjo` + 动态库），主程序编译时展开——宏可以跨项目分发（相当于「代码生成器插件」）。

## 7.3 quote 与插值：用写代码的方式写代码

宏的「输出」是代码，而代码在源码里就是文本。`quote(...)`（引用）让你用**写代码的方式写代码**；`$(表达式)` 是**代码位置的插值**——把变量值/子 Tokens 嵌入模板：

```cangjie
// define/define.cj —— 宏包（7.2 的简化版）
macro package define
import std.ast.*

public macro 调试日志(input: Tokens): Tokens {
    return quote(
        println($(input.toString()))
    )
}
```

两种插值的效果完全不同：

| 写法 | 效果 | 例子 |
|---|---|---|
| `$(input.toString())` | 插入**字符串字面量** | `println("x + 1")`——打印表达式的**文本** |
| `$(input)` | 直接嵌入**代码 token** | `if ($(input) == 0)`——保持为**表达式** |

**注意**：`$()` 只在**代码位置**有效——字符串字面量里不会替换（`"${$(input)}"` 原样输出文本）；`$(input.toString())` 插进字符串字面量同样不会替换——插值只发生在代码位置。

## 7.4 两步编译

宏包与主程序分两步编译——这是宏的「独立编译单元」设计在构建时的体现（三步流程，1.0.5 实测）：

```bash
zhc eject main.zc                           # ① 方言 → 官方源码（main.cj）
cjc define/define.cj --compile-macro       # ② 编译宏包 → define.cjo + lib-macro_define.so
cjc main.cj -o main                        # ③ 编译主程序（import define.* 自动展开宏）
./main                                     # 运行：输出 x + y
```

主程序先 `导入 define.*` 再调用宏：

```cangjie
导入 define.*;

主函数() {
    让 x = 3
    让 y = 4
    @调试日志(x + y)          // 编译期展开为：println("x + y")
}
```

运行输出：`x + y`（宏展开后字符串里是表达式的**文本**，不是值 7）。

> 实测（1.0.5）：`zhc run` **不支持**宏包（`--macro-pkg` 是 `zhc expand` 的参数）——日常验证展开用 `zhc expand main.zc --macro-pkg define/`（自动完成两步编译，见 7.8），或按上面三步手动编译运行。

## 7.5 过程宏进阶：宏里可以跑任意代码

仓颉 1.0 的宏是**过程式风格**（函数式宏）：宏就是普通函数，只是吃 Tokens——宏体内可以循环、匹配、查表。例：生成「循环 N 次」的代码：

```cangjie
// define/define.cj —— 宏包
macro package define
import std.ast.*

public macro 重复(input: Tokens): Tokens {
    return quote(
        for (i in 0..$(input)) {
            println("第${i}次")
        })
}
```

```cangjie
导入 define.*;

主函数() {
    @重复(3)          // 展开为：for (i in 0..3) { println("第${i}次") }
}
```

运行输出（实测）：

```
第0次
第1次
第2次
```

**注意**：这里必须用 `$(input)` 嵌入代码 token（`3`）——如果用 `$(input.toString())` 会插入字符串字面量 `"3"`，展开成 `0.."3"` 就是类型错误。两种插值的差别（7.3 表格）在这一行代码里体现得淋漓尽致。

**注意**：宏内**不能**做类型检查（Tokens 是纯语法）——要类型信息需官方更高级的宏 API（`TypedTokens`）；「编译期求值」是宏与泛型（编译期类型检查）之外，仓颉的第三种编译期机制：宏里的循环、计算都在编译阶段完成，运行时只剩展开结果——把「每次运行都做的重复工作」提前到「编译时做一次」。

## 7.6 派生宏：自动生成样板实现

**是什么**：给类型标 `@派生(相等, 比较)`，编译器自动生成 `相等`/`比较`/`哈希` 等方法——结构体的这些实现**机械重复**（按字段逐个比较），手写又臭又容易错（漏一个字段），派生宏是「约定优于配置」的典范：

```cangjie
// 语法示意（官方 Derive 宏）
结构体 学生 @派生(相等) {
    公开 可变 名字: 字符串
}
```

**注意**：派生条件——字段类型必须支持被派生的操作（如派生 `比较` 要求字段都可比较）；方言 `派生` → 官方 `Derive`；派生宏与手写实现**二选一**（都写了报冲突）；派生宏要求宏库先编译好（两步编译，见 7.4）。

## 7.7 系统宏：@测试 与 @期望

仓颉标准库自带测试框架（`std.unittest`）——`@测试` 标记测试函数、`@期望` 断言：

```cangjie
导入 标准测试宏.*
导入 标准测试.*

函数 加法(甲: 整数, 乙: 整数): 整数 { 返回 甲 + 乙 }

@测试
公开 函数 加法正确() {
    @期望(加法(2, 3), 5)   // 期望表达式的结果为 5
}
```

要点（1.0.5 实测）：

- **两个通配符导入都要写**：`标准测试宏`（测试框架宏本体）与 `标准测试`（断言等运行时类型），缺一不可；
- `@期望(实际值, 期望值)` 宏展开为完整断言代码，失败时给出两侧值；
- `@测试` 标记的函数由框架自动收集执行，无需手动调用。

`zhc test` 在项目根一键运行全部方言测试（转译 → `cjpm test` → 母语化输出）：

```bash
zhc test
```

```
[ 通过 ] 用例： 加法正确
汇总：共 1
    通过： 1, 跳过： 0, 错误： 0
    失败： 0
```

（「共 N」按 `@测试` 函数数统计，1.0.5 实测）

## 7.8 宏展开教学视图：zhc expand

`zhc expand` 查看展开前/后对照（官方 + 反向母语视图，位置映射回方言坐标）：

```bash
zhc expand main.zc --macro-pkg define/
```

实测输出（1.0.5）：

```
═══ zhc expand：宏展开教学视图 ═══
宏包：define/（define）

[展开前] main.zc:4
```

## 7.9 官方对照

宏包内写的**就是官方语法**（`.cj` 文件不经方言转译），所以宏的「官方对照」即宏包源码本身：

```cangjie
// 官方仓颉（与方言宏包完全一致）
macro package define
import std.ast.*

public macro debugLog(input: Tokens): Tokens {
    return quote(
        println($(input.toString()))
    )
}
```

宏包内写的**就是官方语法**（`.cj` 不经方言转译），所以没有「`宏 包` → `macro package`」这类映射；方言侧的区别只有宏名——官方宏名可以直接用中文标识符（如 7.2 的 `调试日志`），系统宏（`派生`/`测试`/`期望`）则在语言包「宏」节配置母语名（`zhc/lang-packs/zh/keywords.toml`）。

## ✳ 设计思想

**① 元编程的时机：先函数，后宏**。90% 的「重复代码」用函数/泛型就能消除；只有当你需要**操作代码本身**（拿到表达式文本、生成语法结构）时，才轮到宏。宏是最后手段，不是第一选择——它牺牲可读性换取表达能力。

**② 编译期 vs 运行期**：宏把「每次运行都做的重复工作」提前到「编译时做一次」——运行时零开销。这是性能哲学：能编译期决定的，绝不拖到运行期；同理，宏崩溃 = 编译错误（好事）——错误在最早时刻暴露。

**③ 卫生与类型：安全元编程**：仓颉宏不会意外捕获调用方变量（卫生宏）、输入输出都是 Tokens（类型化）、宏不能做 IO（设计约束，保证构建可复现）——三条设计让元编程从「危险的黑魔法」变成「受控的代码生成器」。

**④ 约定优于配置**：`@派生(相等)` 一行代替手写几十行样板——「机器能机械生成的，别让人手写」；这也呼应第 11 章的 DRY 原则：单一事实来源，改动只在一处。

## 小结

- 宏包首行 `macro package <名>`（官方语法 + `import std.ast.*`），宏签名 `(Tokens) -> Tokens`，调用 `@宏名(...)`；宏名可用中文；
- 两步编译：`cjc 宏包 --compile-macro` → `cjc 主程序`；`zhc run` 不支持宏包，用 `zhc expand --macro-pkg` 验证；
- `quote()` 构造代码，`$(...)` 只在**代码位置**插值（`$(input)` 嵌代码、`$(input.toString())` 插文本）；区别于字符串插值 `${...}`；
- `@派生(相等)` 自动生成样板实现；`@测试`/`@期望` 是内置测试框架（两个导入缺一不可）；
- `zhc expand` 提供展开教学视图（官方 + 反向母语对照）。
