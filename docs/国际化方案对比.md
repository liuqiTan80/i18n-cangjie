# 国际化（i18n）方案选型对比 —— zhc 语言包机制的定位

> 背景：zhc 的「翻译/国际化」载体是 **TOML 语言包**（`lang-packs/<代码>/`，
> `ZHCLANG` 切换）。本文对比主流 i18n 库/框架与当前方案的优劣与适用场景，
> 并给出新增语言（ko/fr）时的选型结论与术语统一做法。

## 一、推荐库概览

| 库/框架 | 形态 | 核心能力 | 许可 |
|---|---|---|---|
| **GNU gettext** | C 库 + `.po/.mo` 目录式流程 | `msgid→msgstr` 目录、`msgfmt` 编译、复数形式规则（Plural-Forms）、xgettext 提取、生态最老牌 | LGPL/GPL（工具链） |
| **ICU MessageFormat** | 库 + 语法标准 | 占位符 `{name}`、复数/性别 `select`、日期数字本地化格式——CLDR 数据事实标准 | ICU License |
| **Mozilla Fluent** | Rust/JS 实现 + `.ftl` 格式 | **语义键**（`-brand-name` 式命名而非原文当键）、选择器、隔离字符（ isolate）防串排版 | Apache-2.0 |
| **i18next** | JS 生态框架 | 命名空间、回退链（`fr → fr-FR → dev`）、插值、运行时热加载 | MIT |
| **charset4cj**（仓颉 TPC） | 仓颉三方库 | 常用字符编码集合转换——仓颉生态内做**编码层**国际化的基础件，不含消息目录机制 | MulanPSL-2.0 |

## 二、与当前方案（TOML 语言包）对比

| 维度 | gettext | ICU MessageFormat | Fluent | i18next | zhc TOML 语言包（现状） |
|---|---|---|---|---|---|
| 键设计 | 原文当键（msgid） | 原文/语义皆可 | **语义键**（最佳实践） | 语义键 | 语义键（母语词 → 官方名） |
| 复数/性别/选择器 | 复数强（Plural-Forms） | **最强**（CLDR 规则） | 强（select） | 强（插件） | 无（代码关键字翻译不需要） |
| 运行时依赖 | 需 gettext 运行时 | 重（ICU 数据几十 MB） | 轻 | 需 JS 运行时 | **零**（转译期查表，编译产物自包含） |
| 可 diff/审校 | 好（po 工具链） | 一般 | 好 | 一般 | **好**（纯文本 TOML，逐行审校） |
| 贡献门槛 | 需学 po 工具 | 高 | 中 | 低（JS） | **最低**（照现包抄结构填词） |
| 适用场景 | 传统 C/C++ 桌面软件 | 金额/时间等复杂本地化 | 大型产品 UI 文案 | Web 前端 | **编程语言方言映射**（词级 token 替换） |

**结论**：zhc 的翻译对象是**编程语言的关键字/标准库标识符**（词级、无复数、
无插值），gettext/ICU/i18next 的核心增值能力（复数规则、运行时查表）在此
场景用不上，而它们的运行时依赖与工具链门槛反而有害——zhc 的零依赖离线
教学环境（README ②⑤）是硬约束。因此**保持 TOML 语言包结构不变**，但
**借鉴三项最佳实践**落地到新增语言包：

1. **gettext 的目录化流程**：每个语言包自带完整文件清单与版本号
   （`lang_info.toml`），缺文件运行时优雅回退（与 `.po` 缺条目回退 msgid 同构）；
2. **Fluent 的语义键纪律**：键是母语语义词而非官方名变形（韩语 `두다`=let
   而非 `let1`），同一概念全包只用一个词——`keywords.toml` 头注声明
   **术语表**，`scripts/verify-lang-packs.py` 把关撞词；
3. **i18next 的回退链思想**：诊断/界面消息缺键回退中文原文（zhc 已内建），
   新语言先补关键字（能写程序的最低门槛），stdlib/errors/ui 渐进补齐。

仓颉生态侧：若未来要在仓颉**程序内**（而非 zhc 工具链）做 i18n，当前 TPC
仅有 `charset4cj`（编码层）可用，消息目录层暂无成熟三方库——zhc 的 TOML
语言包机制本身即可作为仓颉生态 i18n 的参考实现。

## 三、本次新增语言（ko / fr）

按上述结论新增两个 standard 语言包（与 ru/ja/de/es 同级：关键字 59 全 + 标准库
205 + 模块路径 19 + Top-50 诊断码 + 消息兜底 20 + 界面全表 312——`zhc mapping check`
与九语 E2E 实测通过，2026-09-06 升档；同日 ar 入档 demo 作首个 RTL 试点（详见
[语言包开发](语言包开发.md)第五节·ar RTL 试点要点））；

| 语言 | 目录 | 源码扩展名 | 术语统一约定 |
|---|---|---|---|
| 韩语 한국어 | `zhc/lang-packs/ko/` | `.kc` | 汉字词名词（함수/클래스）+ 하다系动词（두다/던지다）；is 双别名 이다/속하다，public 双别名 공개/공용 |
| 法语 Français | `zhc/lang-packs/fr/` | `.fc` | 无变音符拼写（fonction/soit/ecrire）避免词法切分歧义；is 双别名 est/vaut，public 双别名 public/commun |

冒烟示例（`ZHCLANG=ko`，与 ja 包示例同构）：

```kc
메인() {
    두다 이름: 문자열 = "仓颉"
    출력("안녕하세요, ${이름}！")
}
```

## 四、验证翻译正确加载的方法

```bash
# ① 无 SDK（本仓库 CI / 贡献者本机）：跨语言包五项门禁 + 官方值覆盖集一致
python3 scripts/verify-lang-packs.py

# ② 有 SDK：官方门禁（五项质量门禁 + 跨语言一致性）
cd zhc && cjpm build && ZHC_LANG_PACKS=$PWD target/release/bin/main mapping check

# ③ 有 SDK：端到端运行方言程序（.kc/.fc 需语言包在 ZHC_LANG_PACKS 路径下）
ZHCLANG=ko zhc run examples/hello-ko.kc     # 或任意 .kc 源文件
ZHCLANG=fr zhc run hello.fc

# ④ 查看各包完整度词条数
zhc lang list
```
